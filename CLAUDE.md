# proposit-core — Claude Code Guide

## Generic instructions

- Git commit messages should not include any co-authoring content
- When I report a bug, don't start by trying to fix it. Instead, start by writing a test that reproduces the bug. Then, have subagents try to fix the bug and prove it with a passing test.
- All TypeScript development work must use the `brain-style` skill (specifically its TypeScript sub-skill). Invoke it before writing or reviewing any TypeScript code to ensure naming conventions, casing rules, and style guidelines are followed. Use the TypeScript language server (LSP tool) to verify types, check for errors, and navigate definitions during development.
- After completing a major set of changes, offer to cut a new version via `pnpm version patch|minor|major`. Use `patch` for most changes, `minor` for major feature work, and `major` only when explicitly instructed. When versioning, rename `docs/release-notes/upcoming.md` to `docs/release-notes/v{version}.md` and `docs/changelogs/upcoming.md` to `docs/changelogs/v{version}.md`, then start fresh `upcoming.md` files for subsequent work. After the version bump commit, create a git tag at that commit: `git tag v{version}`. This tag triggers the release and docs deployment workflows.

## Change requests

Detailed change requests live in `docs/change-requests/` as markdown files. When the user mentions a change request, list the files in that folder and check if any filename pertains to the request. If a match looks likely, ask the user to confirm before reading the file. Once confirmed, read the file and use it as the specification for the work. After a change request is fully implemented, delete its markdown file from `docs/change-requests/`.

## Key design rules

Non-obvious constraints enforced by the code that are easy to violate:

- **Root-only operators:** `implies` and `iff` must have `parentId: null`. They cannot be nested. Enforced in `addExpression` and `insertExpression`.
- **`formula` nodes:** Transparent unary wrappers (parentheses). Exactly one child. Collapse rules apply same as operators.
- **Operator nesting restriction:** Non-`not` operator expressions (`and`, `or`, `implies`, `iff`) cannot be direct children of any operator expression. A `formula` node must sit between them. `not` is exempt as a child. Controlled by `grammarConfig.enforceFormulaBetweenOperators` (default: `true`). `fromSnapshot` and `fromData` accept a `grammarConfig` parameter for load-time enforcement control.
- **Granular auto-normalize:** `grammarConfig.autoNormalize` accepts `boolean | TAutoNormalizeConfig`. `true`/`false` enable/disable all normalizations (backward compatible). The object form provides six flags: `wrapInsertFormula` (auto-insert formula buffers in `addExpression`/`insertExpression`/`wrapExpression`), `negationInsertFormula` (auto-insert formula buffer in `toggleNegation` when wrapping a non-not operator in NOT), `collapseDoubleNegation` (collapse NOT(NOT(x)) → x in `toggleNegation`), `collapseEmptyFormula` (auto-collapse operators/formulas after `removeExpression`), `repositionOnCollision` (auto-redistribute sibling positions when a midpoint-computed position collides during `addExpressionRelative`, `appendExpression`, or `promoteChild`; also controls improved child spacing in `insertExpression`), and `absorbSameOperator` (absorb same-operator children through a formula after an operator swap in `updateExpression` — e.g., `AND → formula → AND(B, C)` becomes `AND → [B, C]`). Post-load normalization in `fromSnapshot`/`fromData` only runs when `autoNormalize === true` (boolean); granular config objects skip post-load normalization.
- **Operator collapse:** When `removeExpression` leaves an operator/formula with 0 children, it's deleted (recurses to grandparent). With 1 child, the child is promoted into the operator's slot.
- **Formula collapse rule:** When `collapseEmptyFormula` (or `autoNormalize: true`) is enabled, a formula node is only justified if its bounded subtree (stopping at the next nested formula) contains a binary operator (`and`/`or`). Formulas without binary operator descendants are automatically collapsed by promoting their child. This applies during `removeExpression` (via `collapseIfNeeded`) and via explicit `normalize()` calls.
- **Operator collapse gated on `collapseEmptyFormula`:** Operator collapse (0 or 1 children after removal) only runs when the `collapseEmptyFormula` flag is enabled (either directly or via `autoNormalize: true`). When disabled, the tree is free-form — incomplete or grammar-violating states are allowed.
- **`insertExpression` mutation order:** `reparent(rightNodeId)` runs before `reparent(leftNodeId)` to handle the case where right is a descendant of left's subtree.
- **Premise types are derived:** `isInference()` = root is `implies`/`iff`. `isConstraint()` = anything else or empty. Not stored — derived from expression tree.
- **Derived supporting premises:** Any inference premise not designated as conclusion is automatically supporting. `TCoreArgumentRoleState` only stores `{ conclusionPremiseId? }`.
- **Auto-conclusion assignment:** First premise added to an engine is auto-designated as conclusion if none is set.
- **Variable cascade:** `removeVariable()` cascades across all premises, deleting referencing expressions with operator collapse.
- **Kleene three-valued evaluation:** `true`, `false`, `null`/unknown. All summary flags (`isAdmissibleAssignment`, `isCounterexample`, `preservesTruthUnderAssignment`) are three-valued.
- **`updateExpression` restricted swaps:** Only `and↔or` and `implies↔iff`. `not` cannot be changed (delete and re-create).
- **Publish semantics:** Publishing marks the current version as published and copies it to a new unpublished version. All mutating CLI commands reject published versions.
- **Variables require either claim or premise references:** Every variable must reference either a claim (via `claimId`/`claimVersion`) or a premise (via `boundPremiseId`/`boundArgumentId`/`boundArgumentVersion`), but not both. Claim-bound variables represent atomic propositions; premise-bound variables represent the proposition expressed by the bound premise's expression tree. Internal bindings (`boundArgumentId` matches the engine's argument) are resolved lazily during evaluation. External bindings (different `boundArgumentId`) are evaluator-assigned like claims — use `bindVariableToExternalPremise` or `bindVariableToArgument`. `createPremise` auto-creates a premise-bound variable for each new premise.
- **Libraries are required by ArgumentEngine:** Constructor is `(argument, claimLibrary, claimCitationLibrary, options?)`. The claim library is validated at variable-add time, and `ClaimCitationLibrary` validates both endpoints (and the source-side `type === "citation"` constraint) on every `add()`. `PropositCore` handles the wiring automatically — prefer using `PropositCore` over constructing engines directly.
- **Claim type discriminator:** Every `TCoreClaim` has an immutable `type: 'normal' | 'citation'` field set at creation. `ClaimLibrary.update()` rejects type changes (`CLAIM_TYPE_IMMUTABLE`). Pre-v0.10 snapshots without `type` emit `LEGACY_CLAIM_MISSING_TYPE` at restore time. `'normal'` claims are primary-reasoning propositions; `'citation'` claims represent external/cited content (the unified replacement for the former separate `Source` entity).
- **Claim library:** `ClaimLibrary` is a global, versioned repository with freeze semantics. `freeze()` locks the current version and auto-creates a new mutable copy. No deletion. The pre-v0.10 `SourceLibrary` is gone — sources have been folded into the claim library as `type: 'citation'` claims.
- **Citation acyclicity (`ClaimCitationLibrary`):** Citations are edges in the global claim-citation graph (`citingClaimId` → `sourceClaimId`). `add()` rejects cycles in the citation graph (ID-only — versions don't disambiguate). The source-side claim must have `type: 'citation'` (`CITATION_SOURCE_NOT_CITATION_TYPE`); both endpoints must resolve in the claim library (`CITATION_CITING_REF_NOT_FOUND`, `CITATION_SOURCE_REF_NOT_FOUND`). Create-or-delete only — no update path.
- **`ClaimCitationLibrary` constructor:** Takes a single `claimLookup: TClaimLookup` (and an optional `{ checksumConfig? }`). Both endpoints reference the unified `ClaimLibrary`; there is no separate source lookup.
- **Argument forking:** Forking goes through `PropositCore.forkArgument()`, which creates an independent copy of the argument with new UUIDs, clones all referenced claims (transitively through the citation graph — both `'normal'` and `'citation'` claims), clones the citation edges between them, creates fork records in all five `ForkLibrary` namespaces, and registers the new engine in `ArgumentLibrary`. `canFork()` is a public overridable method on `ArgumentEngine` that subclasses use to inject validation policy (e.g., only fork published arguments). Returns `{ engine, remapTable, claimRemap, argumentFork }` — the legacy `sourceRemap` is gone (citation claims live in `claimRemap` alongside normal claims). For low-level forking without orchestration, use the standalone `forkArgumentEngine()` function. Fork-aware diffing is automatic via `PropositCore.diffArguments()`, which uses `ForkLibrary` records as matchers.
- **`generateId` injection:** All entity ID generation in library files uses `generateId` from `TLogicEngineOptions` (or `TPropositCoreConfig` / `TParserBuildOptions`). Default is `globalThis.crypto.randomUUID()`. CLI files use `randomUUID` from `node:crypto` directly. Never add `import { randomUUID } from "node:crypto"` to `src/lib/` files.
- **No application metadata:** The core library does not deal in metadata such as user IDs, timestamps, or display text. These are application-level concerns. The CLI adds some metadata for its own purposes, but the core schemas are intentionally minimal. Applications extend core types via generic parameters.
- **PropositCore orchestrator:** `PropositCore` is the recommended entry point. It holds all libraries (`ArgumentLibrary`, `ClaimLibrary`, `ClaimCitationLibrary`, `ForkLibrary`) and provides cross-library operations (`forkArgument`, `diffArguments`). Designed for subclassing — all internal state is `protected`. Public fields: `claims`, `claimCitations`, `forks`, `arguments`.
- **ArgumentLibrary:** Engine registry with lifecycle management. Creating engines goes through the library via `create()`. `register()` is for internal use (e.g., forking inserts a pre-built engine).
- **ForkLibrary 5 namespaces:** Fork provenance lives in `ForkLibrary` with five namespaces: `arguments, premises, expressions, variables, claims`. The legacy `sources` namespace is folded into `claims` (citation-typed claims now ride alongside normal claims). Fork records are immutable after creation, no checksums. `ForkNamespace` is a standalone reusable class keyed by `entityId`.
- **Hierarchical checksums:** Every hierarchical entity (expression, premise, argument) carries three checksum fields: `checksum` (meta — entity data only, driven by `checksumConfig`), `descendantChecksum` (from children's `combinedChecksum` values, `null` for leaves), and `combinedChecksum` (equals `checksum` when `descendantChecksum` is null, otherwise `computeHash(checksum + descendantChecksum)`). Dirty flags propagate bottom-up on mutation; recomputation is lazy via `flushChecksums()`. Variables are non-hierarchical (single `checksum`). Role state is folded into the argument's meta checksum. Per-collection checksums are exposed via `getCollectionChecksum()`. `fromSnapshot`/`fromData` accept `checksumVerification?: "ignore" | "strict"`.
- **`orderChangeset` FK-safe ordering:** The `orderChangeset` function in `src/lib/utils/changeset.ts` returns persistence operations in a specific order that satisfies FK constraints: premise updates → expression updates (reparent; skips IDs also in removed) → expression deletes (reverse-topologically sorted) → variable deletes → premise deletes → premise inserts → variable inserts → expression inserts (topologically sorted) → variable updates → argument updates → role updates. The early expression-update phase ensures reparented children are detached from doomed parents before `ON DELETE CASCADE` runs. Expressions appearing in both `modified` and `removed` are dropped from `modified` (the row is about to be deleted). This ordering is an invariant. Any future work that changes entity relationships, adds new entity types, or modifies FK dependencies must preserve or extend this ordering. Flag any planned change that would violate this guarantee.
- **Premise type discriminator:** Every `TCorePremise` now carries an immutable `type: "freeform" | "derivation"` field set at creation. The field is included in `premiseFields` for checksum computation, so premise checksums change on day of upgrade. Pre-v0.11 snapshots without `type` emit `LEGACY_PREMISE_MISSING_TYPE` at restore time. The CLI migration backfills `type: "freeform"` on first v0.11 startup, gated by a `.proposit-v0.11` marker file in the state directory.
- **Derivation premise structure:** A derivation premise (`type: "derivation"`) carries a required, immutable `derivedClaimId`. Its expression tree is locked to two canonical forms: (a) **naked-Q** — a single variable expression at the root referencing the consequent variable bound to `derivedClaimId`; or (b) **implication/biconditional form** — `IMPLIES(antecedent, Q)` or `IFF(antecedent, Q)` with Q as the position-1 child. Any other root type is invalid. The naked-Q form is the initial state when a derivation premise is created and represents "no support given yet." Naked-Q validation depends on `collapseEmptyFormula` being disabled — if auto-normalize collapses the tree, the naked-Q form is destroyed.
- **`ManagedDerivationPremiseEngine`:** Opt-in subclass of `PremiseEngine` that enforces derivation invariants on every mutation. Constructor validates `premise.type === "derivation"` immediately (`DERIVATION_TYPE_MISMATCH`). `fromSnapshot` validates the full expression-tree structure after expressions are loaded (`DERIVATION_STRUCTURE_INVALID`). Mutation overrides (`addExpression`, `appendExpression`, `insertExpression`, `removeExpression`, `updateExpression`, `toggleNegation`, `wrapExpression`, `changeOperator`, `normalizeExpressions`, `loadExpressions`) call `assertWellFormed()` after (or for `loadExpressions`, before) each mutation. Additionally: `removeExpression` and `toggleNegation` block on the consequent expression (`DERIVATION_CONSEQUENT_LOCKED`); `insertExpression` blocks on the consequent slot (`DERIVATION_CONSEQUENT_LOCKED`); `updateExpression` blocks changes to the consequent's `variableId` or `operator` (`DERIVATION_CONSEQUENT_LOCKED`); `changeOperator` on the root blocks swaps to non-implies/iff operators (`DERIVATION_ROOT_OPERATOR_INVALID`). The classic `PremiseEngine` remains permissive — use it when temporarily-invalid states are acceptable.
- **Evaluation pre-flight for derivation premises:** `validateEvaluability()` now includes a derivation structure sweep: every `type: "derivation"` premise is validated via `validateDerivationStructure`. Broken premises produce violations with code `DERIVATION_STRUCTURE_INVALID_AT_EVALUATION` and prevent `evaluate()` and `checkValidity()` from proceeding. Call `validateDerivationStructures()` (the new public method on `ArgumentEngine`) to run only the derivation subset of the sweep without requiring a complete evaluability pass.
- **`ensureClaimBoundVariable`:** Idempotent lookup-or-create on `ArgumentEngine`. If a claim-bound variable for `claimId` already exists in this argument, it is returned unchanged. Otherwise a new variable is created with a fresh UUID, the current claim version from `ClaimLibrary`, and an auto-generated symbol. Throws `CLAIM_NOT_FOUND` if the claim is not in the library. Used internally by derivation premise initialization but also available to callers that need to pin a claim as a variable without creating a full premise.
- **`populateFromCitations` helper:** One-shot method on `ManagedDerivationPremiseEngine`. Takes a `ClaimCitationLibrary` and a `TVariableMaterializer` (typically the `ArgumentEngine`), looks up all citations for `derivedClaimId`, and builds the antecedent: `n=0` → no change (leaves naked-Q intact); `n=1` → `IMPLIES(S1, Q)`; `n≥2` → `IMPLIES(OR(S1,...,Sn), Q)`. Non-recursive — only one level of the citation graph is read. Rejects calls when the antecedent is already non-empty (`DERIVATION_ANTECEDENT_NON_EMPTY`). Internally uses `super.*` calls to bypass mutation overrides during multi-step construction, then validates the final tree with `assertWellFormed()`. For `n≥2`, temporarily switches to `PERMISSIVE_GRAMMAR_CONFIG` so OR can sit directly under IMPLIES without an auto-inserted formula buffer.
- **`iff` two-way propagation in derivation:** When a derivation premise uses `iff` as its root operator, both directions of inference run during evaluation. This means the premise asserts both `antecedent → Q` and `Q → antecedent`, which constrains both sides of the biconditional. Use `iff` when the antecedent is known to be a necessary and sufficient condition for the derived claim.
- **`validateDerivationStructure` standalone utility:** Pure function in `src/lib/utils/derivation-validation.ts`. Takes `(premise: TCoreDerivationPremise, expressions, variables)` and returns `TInvariantValidationResult`. Has no engine dependencies. Exported from the public API (`@proposit/proposit-core`).

## Testing

Tests live in `test/core.test.ts`. Each `describe` block corresponds to a method or logical grouping. All tests build their own fixtures inline — no shared `beforeEach` state. When adding a test for a new feature, add a new `describe` block at the bottom.
