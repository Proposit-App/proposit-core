# proposit-core — Claude Code Guide

## Generic instructions

- Git commit messages should not include any co-authoring content
- When I report a bug, don't start by trying to fix it. Instead, start by writing a test that reproduces the bug. Then, have subagents try to fix the bug and prove it with a passing test.
- All TypeScript development work must use the `brain-style` skill (specifically its TypeScript sub-skill). Invoke it before writing or reviewing any TypeScript code to ensure naming conventions, casing rules, and style guidelines are followed. Use the TypeScript language server (LSP tool) to verify types, check for errors, and navigate definitions during development.
- After completing a major set of changes, offer to cut a new version via `pnpm version patch|minor|major`. Use `patch` for most changes, `minor` for major feature work, and `major` only when explicitly instructed. When versioning, rename `docs/release-notes/upcoming.md` to `docs/release-notes/v{version}.md` and `docs/changelogs/upcoming.md` to `docs/changelogs/v{version}.md`, then start fresh `upcoming.md` files for subsequent work. After the version bump commit, create a git tag at that commit: `git tag v{version}`. This tag triggers the release and docs deployment workflows.

## Change requests

Detailed change requests live in `docs/change-requests/` as markdown files. When the user mentions a change request, list the files in that folder and check if any filename pertains to the request. If a match looks likely, ask the user to confirm before reading the file. Once confirmed, read the file and use it as the specification for the work. After a change request is fully implemented, delete its markdown file from `docs/change-requests/`.

## Key design rules

> **As of 1.0.0.** This section describes the four-tier grammar model
> that landed in `@proposit/proposit-core@1.0.0`. The pre-1.0
> `grammarConfig` / `autoNormalize` / `ManagedDerivationPremiseEngine`
> / `LOAD_GRAMMAR-STRICT_GRAMMAR` machinery is **removed, not
> deprecated**. See `docs/Proposit_Grammar.md` for the full grammar
> reference and §7 there for pre-1.0 → 1.0 upgrade guidance.

Non-obvious constraints enforced by the code that are easy to violate:

### Grammar model

- **Four-tier grammar (`Structural ⊇ Evaluable ⊇ Derivable ⊇ Presentable`):** the AST grammar splits into a strict subset chain. Mutations enforce only Structural and throw on Structural violations. Lower-tier violations (Evaluable, Derivable, Presentable) are queryable via `engine.validate(tier)` and never thrown. See `docs/Proposit_Grammar.md` §2 for the model and §3 for the full rule inventory (S-1..S-14, E-1+E-3..E-7, D-1..D-6, P-1..P-5; codes `E-2` and `D-7` are reserved).
- **Wire format owned by core:** `TGrammarTier`, `TGrammarRuleCode`, and `TViolation` are defined as TypeBox schemas + derived TS types in `src/lib/grammar/types.ts`. Core owns both the rule _definitions_ (what each code means and what triggers it) and the string-literal codes themselves. `@proposit/shared` re-exports them from `@proposit/shared/schemas/grammar` for consumer ergonomics; server and mobile may import from either location. Adding or renaming a rule code is a single-repo coordinated change here — extend the TypeBox union and the validator implementation in the same commit; TypeScript catches drift at build time. The 422 response envelope that composes `TViolation` lives in shared.
- **Two error-code namespaces:** _Engine-error codes_ (in `src/lib/types/validation.ts`) identify thrown errors from engine operations — mutation rejections, schema-validation failures, snapshot load failures, runtime evaluation guards. _Grammar-rule codes_ (`TGrammarRuleCode`, exported from shared) identify returned violations from `validate(tier)`. Both are stable wire format — do not rename either without a coordinated publish.
- **`engine.validate(tier)` short-circuit semantics:** `validate('structural')` returns Structural violations only; `validate('evaluable')` returns Structural + Evaluable; `validate('derivable')` adds Derivable; `validate('presentable')` returns the union across all four tiers. Never throws on grammar issues. Empty array means the argument is at the requested tier or stricter.
- **`engine.normalize(tier?)`:** explicit global pass that runs the auto-normalization rule set everywhere it can fire. Defaults `tier` to `'presentable'`. **Non-destructive in the logical-meaning sense** — never deletes a variable, changes a claim reference, or modifies operator semantics. Cannot recover from Evaluable or Derivable violations (those require user intent via the repair primitives — see the API reference for the current list). In v1.0 every AN rule targets a Presentable invariant, so calls with `tier` ∈ {`structural`, `evaluable`, `derivable`} are effectively no-ops; the parameter is forward-compatible API surface.

### Engine behavior + auto-normalization

- **`behavior: 'assistive' | 'permissive'`:** a single setting on `ArgumentEngine` (default `'assistive'`). In assistive mode, after every successful Structural mutation, the engine runs the AN rule set (AN-1..AN-4) as a uniform post-hook. AN preserves Presentable: if the pre-mutation state was Presentable, the post-mutation state is Presentable. In permissive mode AN does not run; the engine still guarantees Structural integrity but allows the user to settle in lower-tier states. Set via constructor option or `engine.setBehavior(...)`; switching `permissive → assistive` does **not** auto-run `normalize()` — the UI prompts the user explicitly before invoking it.
- **AN rule set:** AN-1 inserts a formula buffer when a non-`not` operator is placed as a direct child of another operator (preserves P-1). AN-2 collapses `NOT(NOT(x))` → `x` (preserves P-2). AN-3 deletes 0-child operators/formulas (recursing to grandparent) and collapses single-child structures where the rule can fire without changing logical meaning (preserves P-3, P-4, incidentally E-1; see `src/lib/grammar/auto-normalize.ts` for exact firing conditions). AN-4 absorbs same-operator parent/grandchild through a formula (preserves P-5). There is **no per-rule opt-in or opt-out** — assistive runs the full set, permissive runs none.
- **Mutations enforce only Structural; never throw on higher tiers:** the mutation API (`addExpression`, `insertExpression`, `wrapExpression`, `removeExpression`, `toggleNegation`, `updateExpression`, `changeOperator`, …) rejects Structural violations with an error. Evaluable / Derivable / Presentable violations never throw at mutation time — they surface via `validate(tier)`. The pre-1.0 `grammarConfig.enforceFormulaBetweenOperators` and per-flag `autoNormalize` config object are gone; mutation enforcement is now driven by Structural rules + the AN post-hook gated on `behavior`.
- **`formula` nodes:** transparent unary wrappers (parentheses). Exactly one child — enforced Structurally (S-13). Mutations that would produce a 0- or multi-child formula throw.
- **Root-only `implies` / `iff` (S-5):** `implies` and `iff` appear at most once per premise and only at the root (`parentId: null`). Mutations that would produce a nested or non-root implies/iff throw.
- **Binary operator arity (S-8):** `implies` and `iff` have exactly two children. The lower-positioned child is the antecedent and the higher-positioned child is the consequent — any `[a, b]` with `a < b` is valid (sibling-position uniqueness is enforced separately by S-9). Mutations that would produce a malformed `IMPLIES(a, b, c)` throw. (Pre-1.0.2 S-8 also pinned the positions to literal `[0, 1]`; that check was over-strict — it false-flagged the engine's own midpoint-spaced bisection pattern from `wrapExpression` / `insertExpression`. Relaxed to arity-only in 1.0.2.)
- **Sibling position uniqueness (S-9):** within a parent's children, no two siblings share the same `position`. Composite mutations that accept a position argument (e.g., `insertExpression`) shift colliding siblings as part of the bundled op; pure structural ops with collisions throw. The pre-1.0 "reposition on collision" was an AN post-hook (the old AN-5) — it's now a Structural mutation-time invariant.
- **Repair primitives:** targeted, **user-initiated** destructive fixes for Evaluable and Derivable violations that `normalize()` cannot resolve (because they would change argument meaning). Each returns the violations it resolved (for UX confirmation messaging / undo / "we made these N changes" feedback). Respect the engine's `behavior` — AN runs after the repair in assistive mode, doesn't in permissive. See the API reference for the current list and signatures.
- **Snapshot loading accepts any Structural state:** `fromSnapshot()` and `fromData()` no longer take a `grammarConfig`. They load any Structural-valid snapshot; lower-tier violations are queryable post-load via `validate(tier)`. The only load failure is a truly broken (non-Structural) snapshot, which throws with the violation list.
- **`insertExpression` mutation order:** `reparent(rightNodeId)` runs before `reparent(leftNodeId)` to handle the case where right is a descendant of left's subtree.
- **Premise types are derived:** `isInference()` = root is `implies`/`iff`. `isConstraint()` = anything else or empty. Not stored — derived from expression tree.
- **Derived supporting premises:** Any inference premise not designated as conclusion is automatically supporting. `TCoreArgumentRoleState` only stores `{ conclusionPremiseId? }`.
- **Auto-conclusion assignment:** First premise added to an engine is auto-designated as conclusion if none is set.
- **Variable cascade:** `removeVariable()` cascades across all premises, deleting referencing expressions with operator collapse.
- **Kleene three-valued evaluation:** `true`, `false`, `null`/unknown. All summary flags (`isAdmissibleAssignment`, `isCounterexample`, `preservesTruthUnderAssignment`) are three-valued.
- **`updateExpression` restricted swaps:** Only `and↔or` and `implies↔iff`. `not` cannot be changed (delete and re-create).
- **Publish semantics:** Publishing marks the current version as published and copies it to a new unpublished version. All mutating CLI commands reject published versions.
- **Variables require either claim or premise references:** Every variable must reference either a claim (via `claimId`/`claimVersion`) or a premise (via `boundPremiseId`/`boundArgumentId`/`boundArgumentVersion`), but not both. Claim-bound variables represent atomic propositions; premise-bound variables represent the proposition expressed by the bound premise's expression tree. Internal bindings (`boundArgumentId` matches the engine's argument) are resolved lazily during evaluation. External bindings (different `boundArgumentId`) are evaluator-assigned like claims — use `bindVariableToExternalPremise` or `bindVariableToArgument`. `createPremise` auto-creates a premise-bound variable for each new premise.
- **Libraries are required by ArgumentEngine:** Constructor is `(argument, claimLibrary, claimCitationLibrary, options?)`. As of v0.12 the third parameter is typed as `TClaimConnectionLookup<TCitation>` (the generic interface implemented by `ClaimCitationLibrary`); axiom validation is not threaded through `ArgumentEngine` — the citation reference is held but never read inside the class, kept as a vestigial slot for backward compat. The claim library is validated at variable-add time, and `ClaimCitationLibrary` validates both endpoints (and the supporting-side `type === "citation"` constraint) on every `add()`. `PropositCore` handles the wiring automatically — prefer using `PropositCore` over constructing engines directly.
- **Claim type discriminator:** Every `TCoreClaim` has an immutable `type: 'normal' | 'citation' | 'axiomatic'` field set at creation. `ClaimLibrary.update()` rejects type changes (`CLAIM_TYPE_IMMUTABLE`). Pre-v0.10 snapshots without `type` emit `LEGACY_CLAIM_MISSING_TYPE` at restore time. `'normal'` claims are primary-reasoning propositions; `'citation'` claims represent external/cited content (the unified replacement for the former separate `Source` entity); `'axiomatic'` claims (added v0.12) represent self-evident propositions invoked as bottom-level support for a derived claim's truth (true-by-definition, historically established, logically required). Axiomatic claim-bound variables are forced to `true` at evaluation — see "Evaluation defaults by claim type" below.
- **Claim library:** `ClaimLibrary` is a global, versioned repository with freeze semantics. `freeze()` locks the current version and auto-creates a new mutable copy. No deletion. The pre-v0.10 `SourceLibrary` is gone — sources have been folded into the claim library as `type: 'citation'` claims. `'axiomatic'` claims (v0.12) live alongside `'normal'` and `'citation'` in the same `ClaimLibrary`; the type discriminator gates which connection library can reference each claim.
- **Citation acyclicity (`ClaimCitationLibrary`):** Citations are connections in the global claim-citation graph (`claimId` → `supportingClaimId`). `add()` rejects cycles (ID-only — versions don't disambiguate). The supporting-side claim must have `type: 'citation'` (`CITATION_SUPPORTING_NOT_CITATION_TYPE`); both endpoints must resolve in the claim library (`CITATION_CLAIM_REF_NOT_FOUND`, `CITATION_SUPPORTING_REF_NOT_FOUND`). Create-or-delete only — no update path. The library implements the generic `TClaimConnectionLibraryManagement<TCitation>` interface; the snapshot wrapper field renamed from `claimCitations` to `connections` in v0.12. `fromSnapshot` runs an unknown-typed pre-check and throws `LEGACY_CLAIM_CITATION_SHAPE` for legacy wrapper or per-entity field names. The reverse-lookup method `getCitationsForSourceClaim` was dropped in v0.12 (no production callers); the forward-lookup `getCitationsForCitingClaim` was renamed to `getConnectionsForClaim`.
- **Axiom library (`ClaimAxiomLibrary`, v0.12):** Parallel class to `ClaimCitationLibrary`, holding axiom-invocation connections (`claimId` → `supportingClaimId`). The dependent-side claim must have `type: 'normal'` (`AXIOM_CLAIM_NOT_NORMAL_TYPE` — citation and axiomatic claims cannot themselves be backed by axioms); the supporting-side claim must have `type: 'axiomatic'` (`AXIOM_SUPPORTING_NOT_AXIOMATIC_TYPE`); both endpoints must resolve in the claim library (`AXIOM_CLAIM_REF_NOT_FOUND`, `AXIOM_SUPPORTING_REF_NOT_FOUND`). **No cycle detection** — axiomatic claims are blocked from the dependent side, so cycles are structurally impossible. Implements the same `TClaimConnectionLibraryManagement<TAxiom>` interface as the citation library, so polymorphic consumer code works against either. Consumed by `ArgumentEngine.populateFromAxioms` (one of the two v1.0 antecedent-population factories — see the `populateFromCitations` / `populateFromAxioms` bullet below).
- **`ClaimCitationLibrary` and `ClaimAxiomLibrary` constructors:** Both take a single `claimLookup: TClaimLookup` (and an optional `{ checksumConfig? }`). Both endpoints of every connection reference the unified `ClaimLibrary`; there is no separate supporting-side lookup. The axiom library uses `claimAxiomFields` from the checksum config when present, falling back to `claimCitationFields`.
- **Argument forking:** Forking goes through `PropositCore.forkArgument()`, which creates an independent copy of the argument with new UUIDs, clones all referenced claims (transitively through a **unified BFS** that consults both `core.citations.getConnectionsForClaim` and `core.axioms.getConnectionsForClaim` at each frontier pop — covers `'normal'`, `'citation'`, and `'axiomatic'` claims), clones the citation and axiom connections between them, creates fork records in all five `ForkLibrary` namespaces, and registers the new engine in `ArgumentLibrary`. The unified BFS guarantees axioms reachable via multi-hop citation paths (and vice versa) end up in the closure. `canFork()` is a public overridable method on `ArgumentEngine` that subclasses use to inject validation policy (e.g., only fork published arguments). Returns `{ engine, remapTable, claimRemap, argumentFork }` — the legacy `sourceRemap` is gone (citation and axiomatic claims live in `claimRemap` alongside normal claims). For low-level forking without orchestration, use the standalone `forkArgumentEngine()` function. Fork-aware diffing is automatic via `PropositCore.diffArguments()`, which uses `ForkLibrary` records as matchers.
- **`generateId` injection:** All entity ID generation in library files uses `generateId` from `TLogicEngineOptions` (or `TPropositCoreConfig` / `TParserBuildOptions`). Default is `globalThis.crypto.randomUUID()`. CLI files use `randomUUID` from `node:crypto` directly. Never add `import { randomUUID } from "node:crypto"` to `src/lib/` files.
- **No application metadata:** The core library does not deal in metadata such as user IDs, timestamps, or display text. These are application-level concerns. The CLI adds some metadata for its own purposes, but the core schemas are intentionally minimal. Applications extend core types via generic parameters.
- **PropositCore orchestrator:** `PropositCore` is the recommended entry point. It holds all libraries (`ArgumentLibrary`, `ClaimLibrary`, `ClaimCitationLibrary`, `ClaimAxiomLibrary`, `ForkLibrary`) and provides cross-library operations (`forkArgument`, `diffArguments`). Designed for subclassing — all internal state is `protected`.
- **PropositCore library field names (v0.12):** Public fields are `claims`, `citations`, `axioms`, `forks`, `arguments` — all single-word nouns. The previous `claimCitations` field was renamed to `citations` for symmetry with the new `axioms` field. The `TPropositCoreSnapshot` slot was renamed in step (`claimCitations` → `citations`, plus a new `axioms` slot); the on-disk filename also renamed (`claim-citations.json` → `citations.json`, plus a new `axioms.json`). `PropositCore.fromSnapshot` runs unknown-typed pre-checks and throws `LEGACY_MISSING_AXIOM_SLOT` (axioms slot absent) or `LEGACY_CLAIM_CITATION_SHAPE` (legacy citation slot/fields) before typed coercion, so non-CLI consumers get an actionable error rather than silent coercion. The CLI handles the migration automatically via the `.proposit-v0.12` marker.
- **Evaluation defaults by claim type (v0.12):** Claim-bound variables evaluate per the claim's `type`. `'normal'` and `'citation'` follow today's behavior — caller assigns; unassigned → `null`. `'axiomatic'` is forced to `true` by a pre-pass in `ArgumentEngine.evaluate` and `ArgumentEngine.checkValidity` (the standalone evaluator stays claim-type-agnostic). Caller assignments for axiomatic-bound variables are rejected pre-flight with `AXIOM_VARIABLE_ASSIGNMENT_FORBIDDEN`. To express "this derivation should not be supported by this axiom," wrap the axiom's antecedent variable expression with `not` via `toggleNegation` — `not(true) = false`, no new mechanism. **`checkValidity` carve-out:** the truth-table enumeration set excludes axiomatic-bound variables (their value is fixed). Citation-bound variables remain in the enumeration set as free choices, so an argument with `k` claim-bound variables of which `a` are axiomatic enumerates `2^(k - a)` assignments. **Propagation note:** the constraint propagator's `trySetChild` will not overwrite an axiom's forced `true`, so rejecting an operator whose only unknown child is axiom-bound is effectively a no-op at the propagation layer (intended behavior).
- **ArgumentLibrary:** Engine registry with lifecycle management. Creating engines goes through the library via `create()`. `register()` is for internal use (e.g., forking inserts a pre-built engine).
- **ForkLibrary 5 namespaces:** Fork provenance lives in `ForkLibrary` with five namespaces: `arguments, premises, expressions, variables, claims`. The legacy `sources` namespace is folded into `claims` (citation-typed claims now ride alongside normal claims; v0.12 axiomatic claims also live in the same `claims` namespace). No fork records are emitted for citation or axiom connections — connections are global and not per-argument. Fork records are immutable after creation, no checksums. `ForkNamespace` is a standalone reusable class keyed by `entityId`.
- **Hierarchical checksums:** Every hierarchical entity (expression, premise, argument) carries three checksum fields: `checksum` (meta — entity data only, driven by `checksumConfig`), `descendantChecksum` (from children's `combinedChecksum` values, `null` for leaves), and `combinedChecksum` (equals `checksum` when `descendantChecksum` is null, otherwise `computeHash(checksum + descendantChecksum)`). Dirty flags propagate bottom-up on mutation; recomputation is lazy via `flushChecksums()`. Variables are non-hierarchical (single `checksum`). Role state is folded into the argument's meta checksum. Per-collection checksums are exposed via `getCollectionChecksum()`. `fromSnapshot`/`fromData` accept `checksumVerification?: "ignore" | "strict"`.
- **`orderChangeset` FK-safe ordering:** The `orderChangeset` function in `src/lib/utils/changeset.ts` returns persistence operations in a specific order that satisfies FK constraints: premise updates → expression updates (reparent; skips IDs also in removed) → expression deletes (reverse-topologically sorted) → variable deletes → premise deletes → premise inserts → variable inserts → expression inserts (topologically sorted) → variable updates → argument updates → role updates. The early expression-update phase ensures reparented children are detached from doomed parents before `ON DELETE CASCADE` runs. Expressions appearing in both `modified` and `removed` are dropped from `modified` (the row is about to be deleted). This ordering is an invariant. Any future work that changes entity relationships, adds new entity types, or modifies FK dependencies must preserve or extend this ordering. Flag any planned change that would violate this guarantee.
- **Premise type discriminator:** Every `TCorePremise` now carries an immutable `type: "freeform" | "derivation"` field set at creation. The field is included in `premiseFields` for checksum computation, so premise checksums change on day of upgrade. Pre-v0.11 snapshots without `type` emit `LEGACY_PREMISE_MISSING_TYPE` at restore time. The CLI migration backfills `type: "freeform"` on first v0.11 startup, gated by a `.proposit-v0.11` marker file in the state directory.
- **Derivation premise structure (Structural + Derivable):** a derivation premise (`type: "derivation"`) carries a required, immutable `derivedClaimId`. Structurally (S-14), its expression tree's root is one of `variable` (naked-Q), `implies`, or `iff`. Derivable (D-1) narrows the populated form further: root must be `implies` (not `iff`) with the consequent at position 1 and the antecedent being either a single claim variable (single-grounding form, D-2) or `OR` of same-grounding-kind claim variables (D-3). Naked-Q is a **valid Derivable state** representing "no support given yet" — it does not require any AN flag to be disabled and is not destroyed by `normalize()`.
- **`ManagedDerivationPremiseEngine` is removed.** Pre-1.0 this subclass enforced derivation invariants on every mutation. In 1.0 those invariants become Derivable rules (D-1..D-6) plus Evaluable rule E-6 (claim-derivation pairing); mutations on derivation premises go through the regular `PremiseEngine`. The IDE/UI surfaces issues via `engine.validate('derivable')` rather than mutation-time throws.
- **Evaluation skips naked-Q derivation premises:** a derivation premise whose tree is a single variable at the root (naked-Q) contributes nothing to `evaluate()` and `checkValidity()` — the evaluator skips it. Naked-Q premises neither assert their consequent nor support its derivation. This replaces the pre-1.0 `DERIVATION_STRUCTURE_INVALID_AT_EVALUATION` throw on naked-Q; the publish-time pruning step (server-side) deletes naked-Q derivation premises before storage, so post-publish arguments never carry them.
- **`ensureClaimBoundVariable`:** Idempotent lookup-or-create on `ArgumentEngine`. If a claim-bound variable for `claimId` already exists in this argument, it is returned unchanged. Otherwise a new variable is created with a fresh UUID, the current claim version from `ClaimLibrary`, and an auto-generated symbol. Throws `CLAIM_NOT_FOUND` if the claim is not in the library. Used internally by derivation premise initialization but also available to callers that need to pin a claim as a variable without creating a full premise.
- **`populateFromCitations` and `populateFromAxioms`** (replace pre-1.0 `populateFromSupports`): two factory methods on `ArgumentEngine`, one per grounding kind. Each looks up its connections for `derivedClaimId` and **atomically replaces** the naked-Q expression tree with the fully-populated antecedent: `n=0` → `kind: 'no-op'` (premise stays naked-Q); `n=1` → `kind: 'populated'` with `IMPLIES(S1, Q)`; `n≥2` → `kind: 'populated'` with `IMPLIES(OR(S1,...,Sn), Q)` (with a `formula` buffer between `IMPLIES` and `OR` in `assistive` behavior per AN-1 / P-1). **Already-populated premises:** both methods **no-op and return `{ kind: 'no-op', state }`** rather than throwing — D-3 (no mixing) is a non-Structural rule, so mutations never throw on it. To switch grounding kinds, the UI must explicitly empty the antecedent via a clearing repair primitive first (no silent dropping of user data, satisfying both the no-changes-without-consent principle and the Structural-only mutation-throw contract). The pre-1.0 `populateFromSupports` mixed citations and axioms into a single `IMPLIES(OR(citations, axioms), Q)` premise, which is illegal under D-3. The migration drops axiom-bound variables from mixed antecedents while keeping citations; see release notes for the audit-trail details.
- **`iff` two-way propagation in derivation:** When a derivation premise uses `iff` as its root operator, both directions of inference run during evaluation. This means the premise asserts both `antecedent → Q` and `Q → antecedent`, which constrains both sides of the biconditional. Use `iff` when the antecedent is known to be a necessary and sufficient condition for the derived claim.
- **D-1 validator (replaces standalone `validateDerivationStructure`):** the pre-1.0 standalone utility folds into the Derivable-tier validator `validateD1` in `src/lib/grammar/validators/derivable.ts`. Callers that need the derivation-structure check in isolation use `validate('derivable')` and filter for the `D-1` code, or import `validateD1` directly. The pre-1.0 export of `validateDerivationStructure` is removed in 1.0.

## Testing

Tests live in `test/core.test.ts`. Each `describe` block corresponds to a method or logical grouping. All tests build their own fixtures inline — no shared `beforeEach` state. When adding a test for a new feature, add a new `describe` block at the bottom.

## Linting notes

- `*.mjs` files are excluded from type-aware ESLint rules — see `disableTypeChecked` override in `eslint.config.mjs`.
- `.claude/` is excluded from Prettier via `.prettierignore`.
- Run `pnpm eslint . --fix` to auto-fix stylistic issues before checking manually.

## ESM import requirements

All relative imports in `src/cli/` and `src/lib/` must end in `.js`. Directory imports must use the explicit index path (e.g. `schemata/index.js`).
