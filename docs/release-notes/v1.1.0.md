# v1.1.0 release notes

Minor release shipping the pipeline framework, the abstract LLM
provider interface, the concrete OpenAI Responses-API provider
extension, and the v1 single-shot argument-ingestion pipeline.
Behaviorally additive: `TParsedArgumentResponse` is unchanged,
`ArgumentParser.build()` is unchanged, and the CLI's `parse`
command keeps its existing arguments. The release lays the
foundation for the multi-stage v2 ingestion pipeline (coming in a
future release) and gives downstream consumers — `proposit-server`,
`proposit-mobile`, third-party callers — a stable, runtime-agnostic
seam for LLM-driven structured-output work.

## What changed

### Pipeline framework — `src/lib/pipelines/`

A small framework for orchestrating LLM-driven workflows as a DAG of
named stages. Three building blocks:

- `executePipeline(pipeline, input, { llm, signal?, onEvent?, concurrencyLimit? })`
  — the scheduler. Validates the input against `pipeline.inputSchema`,
  validates the stage DAG (cycles, self-deps, unknown deps), then
  runs eligible stages concurrently up to `concurrencyLimit` (default
  4). On completion it returns
  `{ output, failures, stageOutcomes, tokenUsage }`.
- `deterministicStage({ id, dependsOn, outputSchema, fn })` — a pure
  (or async-pure) stage with no LLM call.
- `llmStage({ id, dependsOn, outputSchema, model, buildPrompt, tools?, retry?, maxOutputTokens? })`
  — a stage that calls `ctx.llm.respond(...)` with the built prompt,
  validates the response against `outputSchema`, and applies the
  default retry policy (one schema-validation retry, one transient
  retry).
- `subPipelineStage({ id, dependsOn, pipeline })` — runs a nested
  pipeline as a single stage in an outer pipeline. Reserved for
  future composition.

Dependencies are declared with bare-string ids (required) or
`optional("upstream-id")` wrappers (eligibility-only — the downstream
stage runs even when the upstream skipped/failed; `ctx.get(id)`
returns `undefined`). The executor enforces `ctx.get` /
`ctx.stageStatus` strictness: stages can only query upstreams they
declared.

Pipeline-level finalize (`pipeline.finalize.dependsOn` +
`finalize.run`) is its own dependency-aware step. When any required
finalize dep is skipped/failed, finalize is bypassed and the result
has `output: null`. Mid-flight aborts (caller `AbortSignal`) surface
the in-flight stage as `skipped`, not `failed`, so consumers can
distinguish cancellation from a genuine provider error — useful for
server-side task cancellation.

The framework emits a typed event stream
(`pipeline:start` / `stage:start` / `stage:retry` / `stage:end` /
`pipeline:end`) consumed via `onEvent` — the foundation for
server-sent-event observability shipping in a future release.

Public types exported from the package root: `TStage`, `TPipeline`,
`TStageContext`, `TStageStatus`, `TPipelineFinalize`,
`TProcessingFailure`, `TPipelineResult`, `TPipelineEvent`, `TDepSpec`,
`TOptionalDep`, `TRetryPolicy`, `TRetryReason`,
`TExecutePipelineDeps`. Helper values: `executePipeline`,
`optional`, `deterministicStage`, `llmStage`, `subPipelineStage`,
`DEFAULT_RETRY_POLICY`, `PipelineConfigurationError`,
`LlmStageRetryExhaustedError`, `StageAbortedError`,
`SubPipelineFailedError`.

### Abstract LLM provider — `src/lib/llm/`

`TLlmProvider` is the runtime-agnostic LLM seam every stage depends
on. Each provider exposes one method:

```ts
respond<T>(req: TLlmRequest<T>): Promise<TLlmResponse<T>>
```

`TLlmRequest<T>` carries the model, prompt (system + user),
`outputSchema` (a TypeBox `TSchema`), optional tools
(`TToolSpec` discriminated union over `web_search` / `file_search` /
`mcp` / `function`), optional `reasoningEffort`, optional
`maxOutputTokens`, and an optional `AbortSignal`. `TLlmResponse<T>`
returns the structured output, token usage, and a provider-specific
`rawResponseId`.

`src/lib/` carries **zero third-party SDK imports**. Concrete
providers live under `src/extensions/` with `peerDependency`
declarations.

### OpenAI Responses-API provider — `src/extensions/openai/`

`createOpenAiResponsesProvider({ apiKey, model?, baseUrl?, fetch?, maxToolCallRounds? })`
returns a `TLlmProvider` backed by raw `fetch` to
`https://api.openai.com/v1/responses` (the Responses API, not the
deprecated Chat Completions endpoint that the pre-1.1.0 CLI used).
Key behaviors:

- **Structured output via strict mode.** The provider inlines a small
  TypeBox → OpenAI JSON Schema converter (`typeboxToOpenAiSchema`)
  covering the subset the v1 pipeline needs (`Object`, `Array`,
  `String`, `Number`, `Integer`, `Boolean`, `Union` of literals,
  `Literal`, `Optional`, `Record`). Output schemas are submitted with
  `strict: true` so the model can't emit unsanctioned fields.
  `Type.Optional(...)` properties render as `anyOf: [<T>, { type: "null" }]`
  with the property name kept in `required` (the only strict-mode-
  valid encoding of optionality).
- **Function-tool agent loop.** When the model returns one or more
  `function_call` items, the provider executes the matching handlers
  (with the args validated against the tool's `parameters` schema),
  echoes the original `function_call` items + their matching
  `function_call_output` items back into `input` (the Responses API
  requires this echo for conversation-state continuity), and re-calls.
  Loop capped at `maxToolCallRounds` (default 6). Built-in tools
  (`web_search` / `file_search` / `mcp`) execute server-side at
  OpenAI and don't enter the loop.
- **Error classification.** HTTP status routes into typed error
  classes consumers can `instanceof`-check:
    - 5xx → `TransientLlmError` (retried by the framework's default
      retry policy).
    - 429 → `RateLimitLlmError` (not in the default `retryOn`;
      surfaces immediately).
    - 400 → `NonRetryableLlmError` (typically a converter bug or
      malformed request; retrying just burns the second attempt).
    - 422 → `SchemaValidationLlmError` (strict-mode-violation from
      the model; routed through the framework's `schema_validation`
      retry branch for one re-roll).
    - 401 / 403 / other 4xx → `NonRetryableLlmError`.
    - Agent-loop exhaustion → `ToolLoopExhaustedError`
      (non-retryable).
- **Abort propagation.** The caller's `signal` is forwarded to
  `fetch` and surfaces as an `AbortError`, which the framework
  recognizes and routes to `StageAbortedError` so the executor
  records the stage as `skipped` rather than `failed`.

The `openai` npm SDK is declared as an optional `peerDependency`
(`>=4.0.0`) for forward-looking insurance — the v1.1.0 provider does
not import it; runtime uses raw `fetch` only. `grep -r "from \"openai" src/`
returns nothing. The package has a dedicated subpath export at
`@proposit/proposit-core/extensions/openai` for callers that want to
tree-shake the provider out of their build, in addition to the
package-root re-export.

### v1 single-shot argument-ingestion pipeline — `src/extensions/argument-ingestion/`

`createIngestionV1Pipeline(extension, options?)` builds a one-stage
pipeline that calls the configured LLM with the parsing system
prompt + the raw input text, validates the response against the
extension's `responseSchema`, and finalizes into the parser-
consumable `TParsedArgumentResponse` shape — with one extra
`processingFailures: TProcessingFailure[]` slot attached for
observability (always empty in v1; populated by the future
multi-stage pipeline). `basicsExtension` is the default
`TIngestionExtension` value composing the basics-tier per-entity
field shapes from `src/extensions/basics/`.

Behavior is bit-for-bit identical to the pre-1.1.0 CLI parse path
on schema-conformant LLM outputs (gated by a recorded golden corpus
of 5 fixtures: `straightforward`, `with-url-citation`, `with-axiom`,
`ambiguous-conclusion`, `enthymeme`). The new framework adds one
schema-validation retry per LLM stage (default retry policy from
the framework); the pre-1.1.0 direct-call path failed hard on the
first schema-invalid response. That's a usability improvement, not
a regression.

`TParsedArgumentResponse` is unchanged. `ArgumentParser.build()`
is unchanged. CLI consumers still call `parser.validate(response)`
and `parser.build(validated)` after the pipeline returns.

### CLI — `proposit-core arguments parse --pipeline <v1|v2>`

The CLI's `parse` command now routes its LLM call through the v1
pipeline. The new `--pipeline <version>` flag defaults to `v1`;
passing `v2` rejects cleanly with "v2 pipeline not yet shipped —
coming in Phase 2" so users can discover the surface without silent
fallbacks. The flag's other behavior is unchanged: `--api-key`,
`--model`, `--title`, `--description`, `--dry-run` all still work,
and the persisted-argument output path through `ArgumentParser` is
identical to v1.0.2.

## What didn't change

- `TParsedArgumentResponse` schema shape (the `processingFailures`
  slot is additive; the existing fields are unchanged).
- `ArgumentParser` / `BasicsArgumentParser` — both classes are
  byte-identical to v1.0.2. Consumers parsing LLM responses through
  the parser see no behavior change.
- Grammar model (`Structural ⊇ Evaluable ⊇ Derivable ⊇ Presentable`),
  AN-rule set, behavior modes, claim/citation/axiom libraries,
  forking semantics — all unchanged from v1.0.2.
- Existing CLI command surface, persisted snapshot formats, and
  on-disk file shapes.
- `package.json` `dependencies` section. The `openai` peerDep is in
  `peerDependencies` + `peerDependenciesMeta.openai.optional = true`;
  consumers that don't install it pay nothing.

## Cross-repo impact

- `proposit-server` and `proposit-mobile` can bump their
  `@proposit/proposit-core` dep to `^1.1.0` to pick up the new
  pipeline exports. No breaking changes; bumping is optional but
  unlocks server-side ingestion-task wiring (planned for a follow-on
  release).
- The previous chat-completions adapter at `src/cli/llm/openai.ts`
  is replaced by a one-line re-export pointing at the new
  extension; callers that imported `createLlmProvider` from the CLI
  factory still work unchanged.
