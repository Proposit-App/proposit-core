# v1.0.1 release notes

Patch release fixing a contract violation in the engine itself: certain
mutations were leaving the argument in a state that failed core's own
Structural validator (S-8). Affects any consumer that calls
`engine.validate('structural')` — or any superset (`'evaluable'`,
`'derivable'`, `'presentable'`) — after wrapping an expression with an
`implies` or `iff` operator. Discovered while wiring the four-tier
validation gates into `proposit-server`'s publish flow.

## What changed

### `wrapExpression` with `implies` / `iff` now produces S-8-compliant child positions

When `wrapExpression` creates a new binary operator (`implies` or `iff`)
and wraps an existing node with a new sibling, the two children now land
at positions `[0, 1]` exactly — matching the S-8 invariant verbatim.

Previously the engine computed the second child's position as
`midpoint(POSITION_INITIAL, POSITION_MAX)` = `1073741823`, mirroring the
midpoint-spaced pattern used for `and` / `or`. That worked for the
variadic operators but quietly violated S-8 for the binary ones:

> S-8 — Binary operator arity + positions. `implies` and `iff` have
> exactly 2 children, ordered as `[antecedent, consequent]` at positions
> `0` and `1`.

`and` / `or` are unaffected — they keep the midpoint-spaced positions so
future inserts can bisect between siblings.

The same defensive change is applied to the SPLIT path inside
`changeOperator` (the rebalance branch when an operator with 3+ children
is changed to a new binary operator under a formula buffer). That path
is unreachable for `implies` / `iff` today because S-5 throws before the
reparent fires, but the explicit `[0, 1]` positions document the
intended end-state in case S-5 mutation-time enforcement is ever
relaxed.

## Impact

Consumers that run `engine.validate('structural')` (or any stricter
tier) on an engine that has called `wrapExpression` with `implies` or
`iff` will no longer see an erroneous S-8 violation. The fix is purely
local to those code paths; no public API surface or wire format
changed.

No migration is required. Consumers benefit automatically on bump.

## What didn't change

- `POSITION_INITIAL` and `POSITION_MAX` constants are unchanged.
- The `midpoint`-spacing strategy for variadic operators (`and`, `or`,
  `formula`) is unchanged — bisection-friendly headroom is preserved.
- No new error codes, validator codes, or schema fields.
