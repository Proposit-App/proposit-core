## What this slice does

Implements the 12-stage v2-multi-stage ingestion pipeline defined in spec §7.2. The factory `createIngestionV2Pipeline(extension: TIngestionExtension): TPipeline<TIngestionInput, ...>` lives alongside the existing `createIngestionV1Pipeline` in `src/extensions/argument-ingestion/`. The factory's output shape matches v1's (`TParsedArgumentResponse<ExtensionFields> & { processingFailures: TProcessingFailure[] }`) so `parser.build()` is unchanged.

**Substantive new work in this slice:**

1. **Per-stage prompt design.** The spec defines stage IDs, models, dependencies, and output schemas — but NOT the actual prompts. You author them. This is real product work; the prompts shape the quality of the ingestion.
2. **Per-stage TypeBox schemas.** Each LLM stage needs an `outputSchema` matching the "Output" column of spec §7.2.
3. **The 4 deterministic stages.** Real logic: `claim-reference-validation`, `variable-assignment` (with the snake_case-symbol-fallback-to-`p<n>` rule), `formula-compilation` (with the compilation rules in spec §7.3), `formula-validation`.
4. **The factory + DAG wiring.** Compose the 12 stages into a `TPipeline` with correct `dependsOn` declarations (some are `optional(...)` per spec §7.2 — see the Deps column).
5. **The `finalize` step.** Per spec §7.2's last row + §7.4 (role derivation) + §7.5 (failure model). Assembles the extension-shaped response from accumulated stage outputs.
6. **Golden-corpus v2 outputs.** Extend the 5 existing fixtures from slice 1C with v2-recorded expected outputs (against live OpenAI under `INGESTION_TEST_RECORD=1`).

## Per-stage authoring guidance

### LLM stages (8 total): segmentation, claim-mention-extraction, citation-source-detection, axiom-indicator-detection, claim-canonicalization, claim-type-classification, relation-extraction, conclusion-selection

For each LLM stage:

1. **Define the TypeBox output schema** matching the "Output" column in spec §7.2 exactly. Use `Type.Array(Type.Object({...}))` patterns; use `Type.Optional` for fields the LLM may legitimately omit; use `Type.Union([..., Type.Null()])` for nullable-always-present.

2. **Author the system + user prompts** in a `buildPrompt(ctx)` function. The system prompt establishes the stage's role + the output JSON schema (the OpenAI Responses API's strict-mode JSON Schema is generated automatically by `llmStage` from the TypeBox `outputSchema`). The user message interpolates upstream stage outputs via `ctx.get(...)`.

    **Prompt-authoring principles** (read carefully):
    - **Each stage should do ONE thing well.** segmentation just segments; claim-mention-extraction just extracts mentions; etc. Resist the temptation to over-specify (e.g., don't have segmentation also try to classify segments).
    - **Pass upstream context, not derived inferences.** claim-canonicalization gets the raw segments + raw mentions; it doesn't get a pre-computed "guess at the canonical set."
    - **Reference the spec's examples.** The corpus fixtures from slice 1C illustrate what the pipeline should produce; let the v1 expected outputs guide what v2's stages should infer.
    - **Strong models for strong stages.** Spec §6.4 specifies model + reasoning_effort per stage tier (cheap-annotation / medium-extraction / strong-reasoning / strong-hardest). Match exactly.
    - **No hand-coded JSON examples in the system prompt.** Trust strict-mode JSON Schema enforcement; demonstrate format only via `outputSchema`. (Inline examples are fine in the user message if they help disambiguate — but the schema is the contract.)

3. **Wire `dependsOn` per spec §7.2**, using `optional(id)` for the marked dependencies.

4. **Per-stage tests:**
    - Mock the `TLlmProvider` to return a canned response matching `outputSchema`; assert the stage's `run(ctx)` returns the parsed shape.
    - Mock a schema-failing response; assert the framework's retry policy kicks in (the framework handles this; the stage test just confirms it wires through correctly).
    - Mock a transient error; assert the framework retries.

### Deterministic stages (4 total): claim-reference-validation, variable-assignment, formula-compilation, formula-validation

Use `deterministicStage(...)` from `src/lib/pipelines/stage-helpers.ts`. No LLM, no retry, no prompts. Pure functions over upstream context.

**`claim-reference-validation`** (spec §7.2 row 7):

- Reads `claim-canonicalization` output.
- Emits `TProcessingFailure[]` via `ctx.addFailure(...)` for: miniId collisions, dangling mappings (mentionId in `mentionToClaim` not in `claim-mention-extraction` output), empty/whitespace-only claim text.
- Returns... actually wait, the spec says it "doesn't gate downstream" — meaning even if it emits failures, downstream stages still run. The stage's output (`run` return value) is the same failure list. Other stages can `ctx.get('claim-reference-validation')` to read it but most don't need to.

**`variable-assignment`** (spec §7.2 row 8):

- Reads `claim-canonicalization.canonicalClaims`.
- For each canonical claim: validate the `suggestedSymbol` against `/^[a-zA-Z_][a-zA-Z0-9_]{0,31}$/` AND length ≤ 32 AND uniqueness among already-assigned symbols. If valid + unique, use it. Otherwise fall back to `p1`, `p2`, ... in canonicalization order, skipping numbers already used by valid suggested symbols.
- Mint a fresh variable `miniId` for each (separate from the claim's `miniId`); set `claimMiniId` to the canonical claim's id.
- Tests should exhaustively cover: valid suggested symbol, invalid (reserved word, all-uppercase that's not reserved, hyphens, empty, > 32 chars), collision (two claims suggest same symbol; first wins, second falls back), full-fallback (all suggested symbols invalid, all `p<n>` used).

**`formula-compilation`** (spec §7.2 row 11 + §7.3 compilation rules):

- Reads `relation-extraction`, `conclusion-selection`, `variable-assignment`, `claim-type-classification`.
- Compiles each relation to a formula string per the table in §7.3:
    - `support`: `s_symbol IMPLIES t_symbol`
    - `joint-support`: `(s1_symbol AND s2_symbol AND ...) IMPLIES t_symbol`
    - `derivation-support`: `s_symbol IMPLIES t_symbol`
- Mints a dedicated "conclusion premise" (per §7.3 last row + the conclusion-to-premise mapping rule): formula = the conclusion claim's variable symbol alone. `roleHint: 'conclusion'`. Emitted exactly once per pipeline run, regardless of how many relations target the conclusion claim.
- If `conclusion-selection.conclusionMiniId === null`: emit relation premises but `conclusionPremiseMiniId: null`. (`finalize` then reports `argument: null` per §7.5.)
- Use the variable's `symbol` field (looked up via `claimMiniId → ParsedVariable.symbol`), not the claim's `miniId`.

**`formula-validation`** (spec §7.2 row 12):

- Reads `formula-compilation.premises`, `variable-assignment`.
- For each premise's formula: call `parseFormula(formula)` (the existing function from `src/lib/parsing/`). Catch parse errors → emit `ProcessingFailure { code: 'FORMULA_PARSE_ERROR', ... }`.
- For each parsed formula's atoms: check the atom string matches a known variable symbol (from `variable-assignment`). Unresolved atoms → emit `ProcessingFailure { code: 'FORMULA_SYMBOL_UNRESOLVED', ... }`.
- Doesn't gate downstream.

## Factory wiring (`v2-multi-stage.ts`)

```ts
import { type TPipeline, type TIngestionExtension, type TIngestionInput } from "..."
import { /* the 12 stage modules */ } from "./stages/index.js"
import { finalizeResponseV2 } from "./shared/finalize-response-v2.js"

export function createIngestionV2Pipeline(
    extension: TIngestionExtension
): TPipeline<TIngestionInput, /* output shape — see spec §7.0 */> {
    return {
        id: "v2-multi-stage",
        version: "1.0.0",
        inputSchema: /* TIngestionInputSchema */,
        outputSchema: /* extension.responseSchema ∧ { processingFailures: TProcessingFailure[] } */,
        stages: [
            segmentation,
            claimMentionExtraction,
            citationSourceDetection,
            axiomIndicatorDetection,
            claimCanonicalization(extension),       // some stages may parameterize on extension's claimSchema
            claimTypeClassification,
            claimReferenceValidation,
            variableAssignment,
            relationExtraction,
            conclusionSelection,
            formulaCompilation,
            formulaValidation,
        ],
        finalize: {
            dependsOn: [
                "claim-canonicalization",
                "variable-assignment",
                "formula-compilation",
                optional("claim-type-classification"),
                optional("relation-extraction"),
                optional("conclusion-selection"),
                optional("formula-validation"),
                optional("claim-reference-validation"),
            ],
            run: (ctx) => finalizeResponseV2(ctx, extension),
        },
    }
}
```

`finalizeResponseV2` reads the accumulated stage outputs from `ctx.get(...)` and assembles the extension-shaped response per spec §7.2 finalize row + §7.4 (role derivation) + §7.5 (failure model). The output shape must satisfy `TParsedArgumentResponse<ExtensionFields> & { processingFailures: TProcessingFailure[] }` so `parser.build(result.output)` works unchanged.

**Concurrency:** the framework defaults to `concurrencyLimit: 4` which is correct for this pipeline (the segmentation → 3 parallel children fan-out is well-utilized by 4-wide concurrency).

## Golden corpus extension

Slice 1C set up `RecordingLlmProvider` in `test/extensions/argument-ingestion/recording-provider.ts` with a SHA-256 prompt-drift guard. It records LLM calls under `INGESTION_TEST_RECORD=1` for replay during normal test runs. The 5 existing fixtures are `straightforward`, `with-url-citation`, `with-axiom`, `ambiguous-conclusion`, `enthymeme` — see `test/extensions/argument-ingestion/fixtures/<corpus>/`.

**Two recording scenarios** to support:

1. **`recorded-llm.json` + `expected.json`** — v1 single-shot (already exists).
2. **`v2-recorded-llm.json` + `v2-expected.json`** — v2 multi-stage (NEW).

The recording provider should support both modes (e.g., via a pipeline-id-keyed file path inside the fixture folder, or via a constructor parameter). Adjust the existing provider if needed.

**Recording instructions for the dev:**

1. Implement all 12 stages + the factory.
2. Run the unit test suite (mock-provider tests) — confirm green.
3. Author a CLI command (or reuse the existing `proposit-core parse` CLI with a `--pipeline v2` flag if you add one) that runs v2 against a fixture's input text.
4. Set `INGESTION_TEST_RECORD=1` and `OPENAI_API_KEY=...`. Run all 5 fixtures through v2 (one at a time). Verify each fixture's recorded output looks sensible — quality-check the per-stage outputs, fix prompt issues if you see obvious failures.
5. Write the `v2-expected.json` for each fixture (the final assembled response after `finalize`). Hand-author or pretty-print from the recording.
6. Commit the fixtures.
7. Normal `pnpm run test` should then pass against the recordings (replay mode, no `OPENAI_API_KEY` needed).

**Prompt-drift guard:** the existing provider's SHA-256 hash check should also apply to v2 recordings — if you change a v2 stage's `buildPrompt(...)`, the test fails with `RECORDED_PROMPT_STALE: stage <id>` and the dev re-records.

**Fixture corpus parity:** the parity expectations differ per fixture. Add a `parity: { v1: 'strict' | 'v2-strict-upgrade'; v2: 'strict' | ... }` field on each fixture (or follow the slice-1C convention if there's one already). For example, `ambiguous-conclusion` expects `argument: null` in BOTH v1 and v2 (just via different paths); `straightforward` should produce equivalent argument structures.

## Tests

### Unit tests (mock-provider)

One file per stage at `test/extensions/argument-ingestion/stages/<stage>.test.ts`. Coverage:

- **LLM stages:** mock provider returns canned response matching `outputSchema` → assert `run(ctx)` returns the parsed shape. Plus: mock schema-failing response → framework retries. Plus: mock transient error → framework retries. Plus: assert `buildPrompt(...)` returns the expected system + user strings for a known ctx (use a snapshot or string-contains assertion).
- **Deterministic stages:** test each behavioral rule. For `variable-assignment`, test the symbol-validation regex + the fallback sequence exhaustively. For `formula-compilation`, test each compilation rule per spec §7.3 + the conclusion-premise minting. For `formula-validation`, test each `parseFormula` failure mode + symbol-resolution failure.

### Framework integration tests

Extend `test/pipelines.test.ts` if needed for new DAG patterns the v2 pipeline exercises (e.g., a 12-stage pipeline with the fan-out → fan-in topology). Existing framework tests should already cover the primitives; v2's wiring is just consumption.

`test/extensions/argument-ingestion/v2-e2e.test.ts` — for each of the 5 fixtures: replay the recorded v2 LLM responses, run `executePipeline(createIngestionV2Pipeline(basicsExtension), fixture.input, { llm: recordingProvider })`, assert the assembled response matches `v2-expected.json`.

## Out of scope

- Adapter / extension other than `basics` (e.g., `ieee`). The factory is parameterized; future extensions come for free, but only `basics` is shipped + tested here.
- Confidence-gated model escalation (e.g., escalate to flagship if a stage's confidence is low).
- Repair passes that re-run stages on validation failure beyond the framework's existing per-stage retry.
- Server-side integration (that's slice 2D + 2E; this slice ships the library, server adopts in a tiny follow-up).
- Attack/rebuttal relation types — `support`, `joint-support`, `derivation-support` only per spec §7.5.
- Fine-grained discourse markers.
- Pushing the branch or running `pnpm publish`.
