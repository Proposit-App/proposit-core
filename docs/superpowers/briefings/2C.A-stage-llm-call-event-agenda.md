## What this slice does

Add a new variant to the `TPipelineEvent` union in `src/lib/pipelines/types.ts`:

```ts
| {
      kind: "stage:llm-call"
      stageId: string
      attempt: number                              // 1, 2, ... — one event per LLM-call attempt
      prompts: { system: string; user: string }
      output: unknown                               // raw LLM JSON as returned (may not conform to outputSchema if validationError is set)
      tokenUsage: TLlmTokenUsage
      validationError?: string                      // set iff outputSchema rejected this output and a retry follows
      at: number
  }
```

Emit it from `llmStage` (in `src/lib/pipelines/stage-helpers.ts`) **after every LLM-call attempt** — including schema-failed attempts whose retry is about to fire. The emit fires after `ctx.llm.respond` returns and after `Value.Check` runs, but before any retry/return branching. Deterministic stages (no LLM call) emit zero `stage:llm-call` events.

That's the entire core-side change. No new types, no new public functions, no new files.

---

## Why this matters

`proposit-server` slice 2C grows a persistence side-channel that writes per-stage payloads (prompts + raw LLM output + token usage) to a new `pipelineStagePayloads` table for later staff inspection (slice 2F's UI). The bridge has no way to capture prompts + raw output today — the framework's existing events (`stage:start`, `stage:end`, `stage:retry`) carry only metadata. The cleanest boundary is for core to emit one event per LLM-call attempt; the bridge writes one row per event. Single variant carrying optional `validationError` is intentional: the payload shape is identical on success vs validation-failure (same prompts, same `tokenUsage`, same `output`), validation outcome is metadata about the call, not a different event class. Spec §5.2 + the dual-review's Design Question #2 walk the reasoning.

### 2. `src/lib/pipelines/stage-helpers.ts`

The change site is inside the `llmStage` retry loop, currently lines 229-368. The key flow today:

```ts
try {
    const response = await ctx.llm.respond<TOutput>(req)
    if (!Value.Check(config.outputSchema, response.output)) {
        const errors = [...Value.Errors(config.outputSchema, response.output)]
        const validationMessage = errors
            .map((e) => `${e.instancePath}: ${e.message}`)
            .join("; ")
        lastError = {
            reason: "schema_validation",
            code: "OUTPUT_SCHEMA_INVALID",
            message: validationMessage,
        }
        const retryable = policy.retryOn.includes("schema_validation")
        if (!retryable || attempt >= policy.maxAttempts) {
            break
        }
        emitRetry(ctx, config.id, attempt, "schema_validation")
        // ... truncation + userMessage append + sleep + continue
    }

    stashTokenUsage(ctx, config.id, response.tokenUsage)
    return response.output
} catch (err) {
    // ... transient/rate-limit/non-retryable error handling
}
```

You need to insert the `stage:llm-call` emit **right after `Value.Check` runs** so the event has a settled `validationError` value (string when failed, undefined when passed), and **before** the retry/return branching.

Refactored shape (use this as the pattern, adapt as you implement):

```ts
const response = await ctx.llm.respond<TOutput>(req)
const validationPassed = Value.Check(config.outputSchema, response.output)
let validationError: string | undefined

if (!validationPassed) {
    const errors = [...Value.Errors(config.outputSchema, response.output)]
    validationError = errors
        .map((e) => `${e.instancePath}: ${e.message}`)
        .join("; ")
}

ctx.emit({
    kind: "stage:llm-call",
    stageId: config.id,
    attempt,
    prompts: { system: prompt.system, user: userMessage },
    output: response.output,
    tokenUsage: response.tokenUsage,
    validationError,
    at: now(),
})

if (!validationPassed) {
    lastError = {
        reason: "schema_validation",
        code: "OUTPUT_SCHEMA_INVALID",
        // validationError is defined here because validationPassed is false
        message: validationError as string,
    }
    const retryable = policy.retryOn.includes("schema_validation")
    if (!retryable || attempt >= policy.maxAttempts) {
        break
    }
    emitRetry(ctx, config.id, attempt, "schema_validation")
    const truncated = truncateValidationError(
        validationError as string,
        errorCap
    )
    userMessage =
        prompt.user +
        "\n\nYour previous response failed schema validation: " +
        truncated +
        ". Please retry conforming to the schema."
    await sleep(policy.backoffMs, ctx.signal)
    continue
}

stashTokenUsage(ctx, config.id, response.tokenUsage)
return response.output
```

**Critical detail — `prompts.user` is the actual sent message, not the original.** The retry-suffix-appended `userMessage` is what was sent for the current attempt. On attempt 2+, that includes the "Your previous response failed schema validation: …" suffix from the prior attempt's retry path. Emit the as-sent `userMessage`, not the original `prompt.user`. The system prompt doesn't change across attempts so `prompt.system` is fine.

**Error catch block — no `stage:llm-call` emit.** The `catch (err)` block (line 304-352) handles thrown LLM errors (transient, rate-limit, non-retryable, abort). Those didn't return a `response`; there are no prompts/output/tokenUsage to emit. Leave the catch block untouched. The retry-emission via `emitRetry` for transient/rate-limit cases is already there (line 349); keep it.

### 3. `test/pipelines.test.ts`

Add four tests covering the event-ordering examples from spec §5.2:

- **Test 1 — Successful LLM stage:** mock `LlmProvider` returns schema-valid output on first attempt. Assert: exactly one `stage:llm-call` event fires, with `attempt: 1`, `validationError` absent (test via `'validationError' in event === false` or `event.validationError === undefined`), `prompts.system === <expected>`, `prompts.user === <original user message>`. The event must fire BEFORE the `stage:end` event for the same stage (assert via event order).

- **Test 2 — Retry-then-succeed:** mock returns schema-INVALID output on attempt 1, schema-valid on attempt 2 (with retry-appended user message detected in the request). Assert the event sequence: `stage:start` → `stage:llm-call(attempt=1, validationError set)` → `stage:retry(attempt=2)` → `stage:llm-call(attempt=2, validationError absent, prompts.user contains the retry suffix)` → `stage:end(status="completed")`.

- **Test 3 — Retry exhausted (both attempts fail):** mock returns schema-INVALID on both attempts. Assert the event sequence: `stage:start` → `stage:llm-call(attempt=1, validationError set)` → `stage:retry(attempt=2)` → `stage:llm-call(attempt=2, validationError set)` → `stage:end(status="failed")`. Note `stage:end` is `failed`, not `completed`, because `LlmStageRetryExhaustedError` is thrown and converted to a `ProcessingFailure`.

- **Test 4 — Deterministic stage emits zero `stage:llm-call` events:** assemble a pipeline with one `deterministicStage`, run it through `executePipeline`, assert zero events of kind `stage:llm-call` appear.

Use the existing test fixtures + mock provider patterns at the top of `test/pipelines.test.ts` — the file already has a mock `LlmProvider` shape; extend it to support the canned-response-per-attempt patterns Tests 2 + 3 need.

**Watch out:** the existing pipeline tests may have an `onEvent` collector. If they do, reuse it; if they don't, set one up per the executor's `onEvent` callback (you call `executePipeline(pipeline, input, { llm, onEvent: (e) => events.push(e) })` and then assert on `events`).
