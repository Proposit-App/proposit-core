# Migrating from proposit-core 0.10.x to 0.11.0

This guide is for **library consumers** — applications like `proposit-server`, `proposit-mobile`, or any service that embeds `@proposit/proposit-core` and persists its data outside the core's CLI state directory. CLI consumers do not need this guide; the CLI handles its own state via a one-time automatic migration on first v0.11 startup.

v0.11.0 adds derivation premises — a new structurally-constrained premise type with an immutable `derivedClaimId`. It also tightens a few existing APIs.

## Technical summary of changes

### Schemas

- **`TCorePremise`** gains an immutable `type: "freeform" | "derivation"` field. The field is required at creation and cannot be changed afterward. `type` is included in `premiseFields` for checksum computation — premise checksums change on day of upgrade.
- **`TCoreDerivationPremise`** is a new discriminated variant of `TCorePremise` with the additional required field `derivedClaimId: string`.
- **`TFreeformPremise`** is the other variant (`type: "freeform"`); it is structurally identical to the pre-v0.11 premise.

### Libraries / constructor changes

- **`TClaimLookup.getCurrent`** is now **required** (it was previously optional). Any mock or stub that implements `TClaimLookup` with only `{ get }` must add `getCurrent` to compile and run under v0.11.

### New public API

- **`ArgumentEngine.createPremise({ type, derivedClaimId?, extras?, symbol? })`** — typed-bag overload. The legacy positional form `createPremise(extras, symbol)` is still supported via overload.
- **`ArgumentEngine.createPremiseWithId(id, { ... })`** — same typed-bag overload as `createPremise`.
- **`ArgumentEngine.ensureClaimBoundVariable(claimId)`** — idempotent lookup-or-create for a claim-bound variable.
- **`ArgumentEngine.validateDerivationStructures()`** — standalone derivation pre-flight check.
- **`ManagedDerivationPremiseEngine`** — opt-in subclass that enforces derivation rules on every mutation. Import from `@proposit/proposit-core`.
- **`validateDerivationStructure(premise, expressions, variables)`** — standalone pure function. Import from `@proposit/proposit-core`.
- **`TVariableMaterializer`** — minimal structural type for the `argumentEngine` argument of `populateFromCitations`. Import from `@proposit/proposit-core`.

### Evaluation behavior

- `validateEvaluability()` now includes a derivation structure sweep. Broken derivation premises produce issues with code `DERIVATION_STRUCTURE_INVALID_AT_EVALUATION` and cause `evaluate()` / `checkValidity()` to return `{ ok: false }`. If you consume the result of `validateEvaluability()` or `evaluate()`, check for the new code.

### Error codes

New codes to be aware of:

| Code                                          | Scenario                                                                            |
| --------------------------------------------- | ----------------------------------------------------------------------------------- |
| `DERIVATION_TYPE_MISMATCH`                    | `ManagedDerivationPremiseEngine` used with a non-derivation premise.                |
| `DERIVATION_STRUCTURE_INVALID`                | Malformed derivation expression tree (mutation, `fromSnapshot`, `loadExpressions`). |
| `DERIVATION_STRUCTURE_INVALID_AT_EVALUATION`  | Broken derivation tree detected at evaluation time.                                 |
| `DERIVATION_CONSEQUENT_LOCKED`                | Mutation targeting the locked consequent slot.                                      |
| `DERIVATION_ROOT_OPERATOR_INVALID`            | Root operator swap to a non-implication type.                                       |
| `DERIVATION_ANTECEDENT_NON_EMPTY`             | `populateFromCitations` on a premise that already has an antecedent.                |
| `CREATE_DERIVATION_REQUIRES_DERIVED_CLAIM_ID` | Typed-bag `createPremise` with `type: "derivation"` but no `derivedClaimId`.        |
| `CREATE_DERIVATION_CLAIM_NOT_FOUND`           | `createPremise` derivation path, claim not in library.                              |
| `CLAIM_NOT_FOUND`                             | `ensureClaimBoundVariable` but claim not in library.                                |
| `LEGACY_PREMISE_MISSING_TYPE`                 | Snapshot restore for a premise record that lacks `type`. Use as migration trigger.  |

## Detection

To detect whether a stored snapshot is pre-v0.11, check whether premise records have a `type` field. Pre-v0.11 records will not. If you call `ArgumentEngine.fromSnapshot()` on legacy data, core will raise a validation error with code `LEGACY_PREMISE_MISSING_TYPE`. You can either:

- Catch that error and run your migration on the fly, or
- Pre-scan your storage and migrate eagerly during deploy.

The eager approach is recommended for production systems.

## Step-by-step migration

### 1. Backfill `type: "freeform"` on existing premises

For every pre-existing premise record in your storage, set `type: "freeform"`. No other field changes are needed — this is a pure addition.

### 2. Recompute premise checksums

The `type` field is part of `premiseFields` in the checksum config, so premise checksums change. Recompute:

- All premise `checksum`, `descendantChecksum`, and `combinedChecksum` values.
- The owning argument's checksum (argument checksum depends on premise checksums transitively).

Variable and expression checksums are unaffected.

### 3. Update `TClaimLookup` implementations

If your code provides a custom `TClaimLookup` implementation (for example, as a test double or adapter), add the `getCurrent(id: string): TClaim | undefined` method. The signature matches the existing `ClaimLibrary.getCurrent`.

## Code-level API changes

### `createPremise` / `createPremiseWithId`

**Heuristic for overload routing:** The typed-bag form is triggered when the first argument to `createPremise` (or second argument to `createPremiseWithId`) is an object that contains a `type` key. If your existing `extras` object happens to contain a `type` key, the call will silently route to typed-bag mode — this is a **known breaking change**. Rename the `type` key in your extras (e.g., to `kind`) before upgrading if your code is affected.

Before:

```typescript
engine.createPremise({ type: "myapp-premise" }, "P")
```

After (rename the extras key):

```typescript
engine.createPremise({ kind: "myapp-premise" }, "P")
// or use typed-bag form:
engine.createPremise({
    type: "freeform",
    extras: { kind: "myapp-premise" },
    symbol: "P",
})
```

### Using `ensureClaimBoundVariable`

```typescript
// Idempotent — safe to call multiple times for the same claimId
const variable = engine.ensureClaimBoundVariable(claimId)
```

### Using `populateFromCitations`

Requires a `ManagedDerivationPremiseEngine` instance. If you create derivation premises through `createPremise`, the returned `PremiseEngine` is the base class. Use a factory or subclass approach to get managed engines:

```typescript
import { ManagedDerivationPremiseEngine } from "@proposit/proposit-core"

// After createPremise returns:
const { result: pm } = engine.createPremise({
    type: "derivation",
    derivedClaimId,
})
// pm is a PremiseEngine — cast or create a ManagedDerivationPremiseEngine from its snapshot
const managedPm = ManagedDerivationPremiseEngine.fromSnapshot(
    pm.snapshot(),
    argument,
    variableManager
)
managedPm.populateFromCitations(claimCitationLib, engine)
```

### `_generateId` in `fromSnapshot` (known rough edge)

`ManagedDerivationPremiseEngine.fromSnapshot` accepts an optional `generateId` parameter to inject a custom ID generator into the instance (used internally by `populateFromCitations`). This is a known rough edge — the injection uses a property assignment on the prototype-upgraded instance. It works correctly but the API may be cleaned up in a future minor version.

### Error code handling

Audit any `try/catch` or error-code-string-match that may be affected by the new codes listed above. In particular:

- If you call `evaluate()` and pattern-match on `issues`, check for `DERIVATION_STRUCTURE_INVALID_AT_EVALUATION`.
- If you restore snapshots from storage, catch `LEGACY_PREMISE_MISSING_TYPE` to trigger your migration.

## Rollback

If you need to roll back to v0.10.x after migrating data, you will need to remove the `type` and `derivedClaimId` fields from premise records and recompute premise checksums. There is no automated rollback path.
