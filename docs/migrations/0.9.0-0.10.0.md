# Migrating from proposit-core 0.9.x to 0.10.0

This guide is for **library consumers** — applications like `proposit-server`, `proposit-mobile`, or any service that embeds `@proposit/proposit-core` and persists its data outside the core's CLI state directory. CLI consumers do not need this guide; the CLI handles its own state via a one-time automatic migration on first v0.10 startup.

v0.10.0 unifies the `Source` entity with `Claim`. There is no longer a separate source table — sources are claims with `type: "citation"`. Citation associations (formerly `ClaimSourceAssociation`) are now `ClaimCitation` records that link two claims.

The migration touches your schema, your persisted data, your fork records, and several constructor signatures. None of it is automatic for embedders. The good news is that the shape change is mechanical — there is no data loss, no semantic ambiguity, and the migration can be performed offline before the first v0.10 deploy.

## Technical summary of changes

### Schemas

- **`TCoreClaim`** gains an immutable `type: "normal" | "citation"` field. The field is required at creation and cannot be changed afterward.
- **`TCoreSource`** is deleted. Its fields collapse into citation-typed claims. The IEEE source extension schema (`IEEESourceSchema`) is replaced by `IEEECitationClaimSchema`.
- **`TCoreClaimSourceAssociation`** is renamed `TCoreClaimCitation`. Field renames: `sourceId` → `citedClaimId`, `sourceVersion` → `citedClaimVersion`. The "claimant" side (the claim doing the citing) keeps its `claimId` / `claimVersion` field names.

### Libraries

- **`ClaimSourceLibrary`** is renamed `ClaimCitationLibrary`. Its constructor used to take two lookups (`claimLookup`, `sourceLookup`). It now takes a single `claimLookup` because both sides of a citation edge are claims.
- **`ClaimCitationLibrary.add()`** rejects two new error conditions:
  - The cited claim is not citation-typed (`CITATION_SOURCE_NOT_CITATION_TYPE`).
  - Adding the edge would create a cycle in the citation graph (`CITATION_CYCLE_DETECTED`). Acyclicity is checked via DFS on every `add()`.

### Snapshots

- **`TPropositCoreSnapshot`** field renames:
  - `sources` is removed. Citation-typed claims live in `claims` alongside normal claims.
  - `claimSources` is renamed `claimCitations`.
- There is no compatibility shim. Consumers that round-trip snapshots over HTTP or other transports must accept the new field names on both sides.
- Collection-level checksums for `claims` and the renamed `claimCitations` collection shift on day of upgrade because the underlying entity shapes changed. Argument and expression checksums are unaffected — variables reference claims by `(id, version)`, not by checksum.

### ForkLibrary

- Fork namespaces drop from 6 to 5: `arguments`, `premises`, `expressions`, `variables`, `claims`. The `sources` namespace is folded into `claims`.
- `forkArgument()` no longer takes a `sourceLibrary` argument.

### Constructors

- **`ArgumentEngine`** constructor now takes 4 library arguments instead of 5. The `sourceLibrary` parameter is removed; the former `claimSourceLibrary` parameter is renamed `claimCitationLibrary`.
- **`PropositCore`** constructor drops its `sourceLibrary` parameter.

### Error codes

- Renames: `ASSOC_*` → `CITATION_*`. Audit any code that string-matches these codes.
- New codes:
  - `CLAIM_TYPE_IMMUTABLE` — raised on attempted post-creation type change.
  - `LEGACY_CLAIM_MISSING_TYPE` — raised on snapshot restore when a claim record has no `type` field. Use this as your migration trigger.
  - `CITATION_SOURCE_NOT_CITATION_TYPE` — raised when adding a citation edge whose cited claim has `type: "normal"`.
  - `CITATION_CYCLE_DETECTED` — raised when adding a citation edge would create a cycle.

## Detection

To detect whether a stored snapshot is pre-v0.10, check whether claim records have a `type` field. Pre-v0.10 records will not. If you call `PropositCore.fromSnapshot()` on legacy data, core will raise a validation error with code `LEGACY_CLAIM_MISSING_TYPE`. You can either:

- Catch that error and run your migration on the fly, or
- Pre-scan your storage and migrate eagerly during deploy.

The eager approach is recommended for production systems.

## Step-by-step migration

The order below avoids intermediate states that would fail validation. Run all steps as part of a single transaction or migration job per dataset.

### 1. Convert sources to claims

For each `Source` record in your storage:

- Insert a corresponding `Claim` record with the same `id` and `version`. Preserve `id` exactly so existing references (citations, fork records) continue to resolve.
- Set `type: "citation"`.
- Map source fields to claim fields. The IEEE extension's `IEEESourceSchema` corresponds 1:1 to `IEEECitationClaimSchema`.
- If you stored a custom extra named `type` on source records, rename it (for example to `kind`) before this step. The new schema reserves `type` as the discriminator and rejects conflicting extras.

After this step, delete the original source records.

### 2. Backfill `type: "normal"` on existing claims

For every pre-existing claim record, set `type: "normal"`. Do not overwrite the citation-typed claims you just inserted.

### 3. Rename association records

For each `ClaimSourceAssociation` record:

- Rename the table/collection to `ClaimCitation` (or its equivalent in your storage).
- Rename `sourceId` → `citedClaimId` and `sourceVersion` → `citedClaimVersion`.
- The `claimId` and `claimVersion` fields keep their names.

### 4. Fold fork records

If you persist `ForkLibrary` data:

- Move every record in the `sources` namespace into the `claims` namespace under the same `entityId`. Fork records do not carry an entity-type discriminator, so the move is straightforward.
- Drop the `sources` namespace.

### 5. Recompute checksums

The `type` field is part of `claimFields` in the new checksum config, so claim checksums change. Citation-association checksums change because the field names changed. Recompute:

- All claim `checksum` values.
- All citation `checksum` values.
- The `claims` and `claimCitations` collection-level checksums.

Argument-level checksums (and the expression and variable checksums underneath them) are unaffected because variables reference claims by `(id, version)`, not by claim checksum. You do not need to retouch arguments.

### 6. Validate acyclicity

`ClaimCitationLibrary.add()` rejects cycles, but legacy data might already contain a cycle that pre-v0.10 code allowed (the old `ClaimSourceLibrary` did not check). Before going live:

- Build a directed graph of citation edges (citing claim → cited claim).
- Run a DFS or topological sort to detect cycles.
- If you find any, repair them (typically: remove the offending edge or split a circular reference) before importing into v0.10. There is no `force` flag — the library will reject the snapshot otherwise.

## Code-level API changes

The migration also requires source-level updates to your application code. The most common touch points:

### Claim creation

Before:

```typescript
const claim = claimLib.create({ /* fields */ })
```

After:

```typescript
const claim = claimLib.create({ type: "normal", /* fields */ })
// or
const citation = claimLib.create({ type: "citation", /* fields */ })
```

### Citation library construction

Before:

```typescript
const assocLib = new ClaimSourceLibrary(claimLookup, sourceLookup)
```

After:

```typescript
const citationLib = new ClaimCitationLibrary(claimLookup)
```

### `ArgumentEngine` construction

Before (5 library args):

```typescript
new ArgumentEngine(argument, claimLib, sourceLib, claimSourceLib, options)
```

After (4 library args):

```typescript
new ArgumentEngine(argument, claimLib, claimCitationLib, options)
```

The `claimSourceLibrary` parameter is renamed `claimCitationLibrary`.

### `PropositCore` construction

Drop the `sourceLibrary` parameter. Most apps wire libraries through `PropositCore` rather than constructing engines directly, so this is the most likely touch point.

### Error code handling

Audit any `try/catch` or error-code-string-match that references `ASSOC_*` codes; rename to `CITATION_*`. Add handlers for the four new codes (`CLAIM_TYPE_IMMUTABLE`, `LEGACY_CLAIM_MISSING_TYPE`, `CITATION_SOURCE_NOT_CITATION_TYPE`, `CITATION_CYCLE_DETECTED`) where appropriate.

## Rollback

If you need to roll back to v0.9.x after migrating data, you will need to reverse step 1 (split citation-typed claims back out into source records), step 3 (rename citation records back to associations), step 4 (re-introduce a `sources` fork namespace), and recompute checksums again. There is no automated rollback path — plan your deploy accordingly. The recommended posture is: stage the migration on a copy of production data, validate it under v0.10 with `checksumVerification: "strict"`, and only then cut over.
