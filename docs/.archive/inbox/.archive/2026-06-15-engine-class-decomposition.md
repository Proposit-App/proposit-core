# Follow-up: Decompose `ArgumentEngine` and `PremiseEngine`

**Date:** 2026-06-15
**Origin:** Split out of `2026-06-15-lib-extensions-architecture-review.md` during triage.
**Status:** Deferred — needs closer inspection before any work begins.

---

## Why this is a separate item

These two are the largest engine classes in the codebase and the most invariant-dense. The mutation methods interleave three concerns that must stay consistent: the `withValidation` wrapper, the `ChangeCollector` lifecycle, and checksum dirty-set propagation. Mutations also obey the rule that **only Structural violations throw** at mutation time (Evaluable/Derivable/Presentable are queried via `engine.validate(tier)`). Any extraction risks silently breaking that contract, so these were ranked **high-effort / high-regression-risk** and pulled out of the main review to be done last, one method-family at a time, behind the existing test suite.

## Targets

### src/lib/core/argument-engine.ts — 2,861 lines

The single largest file. Exports `ArgumentEngine` (~125-method class) plus supporting types/functions, carrying premise lifecycle, expression-mutation orchestration, checksum wiring, validation, and library operations in one class.

Candidate seams:

- **Premise lifecycle** (add/remove premises, manage the `Map<string, PremiseEngine>`) → `premise-lifecycle.ts`
- **Variable management** (`VariableManager`, expression-index wiring) → already in `variable-manager.ts`; collapse the references here into that class's API surface.
- **Checksum orchestration** (dirty propagation across premises) → `checksum-orchestration.ts`
- **Premise-level mutation** (the `change*` methods, which already delegate to `PremiseEngine`) → extract the bulk into a `PremiseChangeBatcher` or similar.

### src/lib/core/premise-engine.ts — 2,284 lines

Implements 13 interfaces. Every mutation method (`addExpression`, `appendExpression`, `insertExpression`, `wrapExpression`, …) repeats the same `withValidation` + `ChangeCollector` + expression-by-variable indexing pattern ~10 times.

Candidate seams:

- **Mutation boilerplate** (`withValidation` + collector setup) → a higher-order `wrapWithValidation(fn, ...)` or an abstract base with a protected template method.
- **Expression operations** (9 methods already delegated to `ExpressionManager`) → thin veneers; evaluate whether they need public surface or can be generated by composition in the constructor.
- **Checksum management** (`flushChecksums`, `markDirty`, sync helpers) → extract to a `PremiseChecksum` module/mixin.

## Constraints to verify before starting

- Public method signatures on `ArgumentEngine` / `PremiseEngine` are part of `[Public-Engine-API]` (CLAUDE.md Documentation Sync) — extractions must preserve the public surface and the JSDoc on the interface files.
- Mutation-time throw semantics (Structural only) must be preserved exactly.
- Checksum dirty-set ordering (bottom-up, depth-sorted) must not change behavior.
- Do these in small increments, each proven by the existing `test/core.test.ts` suite (add reproducers where a seam is non-obvious).
