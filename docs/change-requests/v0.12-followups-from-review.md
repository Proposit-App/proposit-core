# v0.12.0 follow-ups — review findings worth acting on

## Context

After cutting v0.12.0, a code review of the release surface was run against the `qwen3.6:latest` model via the ollama MCP, chunked across schemata, libraries, engine, CLI, and migration. Most flagged items were design observations, false positives, or restatements of existing intent. This change request collects the findings that (a) describe real bugs or sharp edges and (b) are scoped tightly enough to land as a small follow-up without re-opening v0.12 design decisions.

This is intentionally narrow. Items deferred or rejected from the review are listed at the bottom.

---

## Change 1 — `populateFromSupports` must dedupe overlapping supports

### Problem

`ManagedDerivationPremiseEngine.populateFromSupports` builds an OR-of-supports antecedent from `citationLib.getConnectionsForClaim(derivedClaimId)` concatenated with `axiomLib.getConnectionsForClaim(derivedClaimId)`. The same `supportingClaimId` appearing **twice within the citation list itself** is not prevented by `ClaimCitationLibrary.add` (no uniqueness check on the `(claimId, supportingClaimId)` pair — only `id` is checked). A claim cited twice from another claim with two different connection IDs would produce two OR children referencing the same `variableId`.

(The cross-library overlap case — same claim appearing as both a citation and an axiom supporting endpoint — is structurally impossible because claim `type` is immutable and the supporting-side type checks (`CITATION_SUPPORTING_NOT_CITATION_TYPE`, `AXIOM_SUPPORTING_NOT_AXIOMATIC_TYPE`) reject mismatches at `add()`. The intra-list duplication is the only realistic path today.)

### Evidence

- `src/lib/core/managed-derivation-premise-engine.ts:441-468` — citations and axioms iterated, supporting variables pushed in order without a dedupe step.
- `src/lib/core/managed-derivation-premise-engine.ts:464-468` — variable-manager-side dedupe (`hasVariable(sv.id)`) prevents duplicate _variables_, but the `supportingVariables` array still contains duplicates, so `buildAntecedentFromSupportingVariables` emits duplicate variable _expressions_ into the OR.
- `src/lib/core/argument-engine.ts:1024-1035` — `ensureClaimBoundVariable` returns the existing variable when one is already bound, confirming the same `variableId` is reused.

### Proposed change

In `populateFromSupports`, dedupe by `supportingClaimId` before materializing variables. Preserve the order rule (citations first, axioms second; source order within each). Document the rule in the JSDoc.

```ts
const seen = new Set<string>()
const orderedSupports: string[] = []
for (const conn of citationConnections) {
    if (!seen.has(conn.supportingClaimId)) {
        seen.add(conn.supportingClaimId)
        orderedSupports.push(conn.supportingClaimId)
    }
}
for (const conn of axiomConnections) {
    if (!seen.has(conn.supportingClaimId)) {
        seen.add(conn.supportingClaimId)
        orderedSupports.push(conn.supportingClaimId)
    }
}
const supportingVariables = orderedSupports.map((id) =>
    argumentEngine.ensureClaimBoundVariable(id)
)
```

### Alternative considered — library-layer edge uniqueness

A root-cause alternative would be to enforce `(claimId, supportingClaimId)` uniqueness in `ClaimCitationLibrary.add()` (and symmetrically in `ClaimAxiomLibrary.add()`) via two new error codes `CITATION_DUPLICATE_EDGE` / `AXIOM_DUPLICATE_EDGE`. That fixes the failure at the source rather than asking every consumer to dedupe.

Deferred from this change request because: (a) the library currently accepts duplicate edges by design — two citation rows from claim A to claim B with different connection ids are a representable shape that no production caller has been told to avoid; (b) adding the uniqueness constraint is a breaking change for any out-of-tree consumer relying on multiple-edges-per-pair semantics, which is outside the scope of a v0.12 follow-up. Worth re-opening in a later release after confirming no consumer relies on the shape.

### Test plan

Per CLAUDE.md, the failing test lands first as its own commit, then the fix in a follow-up commit. Add to `test/core.test.ts` under the `populateFromSupports` describe block:

1. Two citations on the same derived claim pointing at the same supporting claim → antecedent shape is `IMPLIES(VarExpr(S), Q)` (n=1 form), not `IMPLIES(formula(OR(S, S)), Q)`.
2. Three citations on the same derived claim — two pointing at supporting claim S and one at T — → antecedent shape is `IMPLIES(formula(OR(S, T)), Q)`, source-order preserved with the duplicate collapsed at first occurrence.
3. Existing tests must continue to pass — the order-preservation rule (citations first, axioms second) is not relaxed.

## Change 2 — `applyAxiomaticForcedAssignments` must use key presence, not `!== undefined`

### Problem

`applyAxiomaticForcedAssignments` rejects a caller-supplied assignment to an axiomatic-bound variable. The current guard is `callerVariables[claimBound.id] !== undefined`, which lets an explicit `undefined` slip through silently and be overwritten to `true`. The intent is to reject _any_ attempt by the caller to address the key.

### Evidence

- `src/lib/core/argument-engine.ts:2314` — `if (callerVariables[claimBound.id] !== undefined)`.

### Proposed change

```ts
if (Object.hasOwn(callerVariables, claimBound.id)) {
    throw new InvariantViolationError([
        {
            code: AXIOM_VARIABLE_ASSIGNMENT_FORBIDDEN,
            // ...existing message...
        },
    ])
}
```

### Test plan

Per CLAUDE.md, the failing test lands first as its own commit, then the fix in a follow-up commit. Add to `test/core.test.ts` under the axiom evaluation describe block:

1. Passing `{ [axiomaticVarId]: undefined }` in `assignment.variables` throws `AXIOM_VARIABLE_ASSIGNMENT_FORBIDDEN` (today it silently coerces to `true`).
2. Passing `{ [axiomaticVarId]: true }` still throws (no regression — already covered).
3. Passing no entry at all still forces the variable to `true` and evaluation proceeds (no regression).

## Change 3 — Tighten `migrateV012` marker-detection catch

### Problem

`migrateV012` uses `await fs.access(markerPath)` inside a bare `try { ... } catch {}` to decide whether the marker is present. Any error — including EACCES, EIO, or a directory existing where the marker file is expected — is treated as "marker missing, proceed with migration." A permission error on the marker would cause the migration to re-execute on every CLI invocation, with the rest of the script's idempotency saving us from data corruption but not from repeated work and noise on stderr.

### Evidence

- `src/cli/storage/migrate-v0.12.ts:36-41` — bare catch on `fs.access`.
- Sibling step at `:46-50` (`fs.mkdir`) has the same shape but is genuinely best-effort — leave as is.

### Proposed change

Distinguish ENOENT from other errors on the marker check. Treat ENOENT as "not yet migrated"; surface anything else. The sibling `fs.mkdir(stateDir, { recursive: true })` block keeps its bare catch (it's genuinely best-effort — subsequent file writes will surface any real failure with file-specific context); a one-line comment is added there to spell out the contrast with the now-tightened access catch.

```ts
try {
    await fs.access(markerPath)
    return // Already migrated.
} catch (err) {
    if ((err as NodeJS.ErrnoException).code !== "ENOENT") {
        throw err
    }
    // Marker missing — proceed with migration.
}
```

### Test plan

This is awkward to unit-test cleanly (requires simulating permission errors on a marker file). Acceptable coverage: a regression check in `scripts/smoke-test.sh` confirming the migration runs exactly once across two CLI invocations (the marker case). The EACCES case is documented and left to manual verification.

## Change 4 — `remove` methods on connection libraries throw `InvariantViolationError`

### Problem

`ClaimAxiomLibrary.remove` and `ClaimCitationLibrary.remove` both throw a plain `Error` when the connection id is unknown. Every other error path in these libraries throws `InvariantViolationError`. The in-tree CLI consumers (`src/cli/commands/citations.ts`, `src/cli/commands/axioms.ts`) pre-check existence and never reach this throw, so no existing caller is broken by the current shape — this change is forward-looking consistency for external library consumers, who would otherwise need to special-case these two methods when branching on error type.

### Evidence

- `src/lib/core/claim-axiom-library.ts:171` — `throw new Error(\`ClaimAxiom "${id}" not found.\`)`.
- `src/lib/core/claim-citation-library.ts:169` — `throw new Error(\`ClaimCitation "${id}" not found.\`)`.

### Proposed change

Add two new error codes (mirroring the existing CITATION*/AXIOM* naming) and throw via `InvariantViolationError`:

- `CITATION_NOT_FOUND` in `src/lib/types/validation.ts`.
- `AXIOM_NOT_FOUND` in `src/lib/types/validation.ts`.

Throw from each `remove` with the same id-not-found context (`entityType`, `entityId`).

### Test plan

Per CLAUDE.md, the failing test lands first as its own commit, then the fix in a follow-up commit. Add tests to `test/core.test.ts`:

1. `ClaimAxiomLibrary.remove("missing")` throws `InvariantViolationError` whose first violation has code `AXIOM_NOT_FOUND`.
2. Same for `ClaimCitationLibrary.remove("missing")` with `CITATION_NOT_FOUND`.
3. Existing tests on successful remove continue to pass.

Docs: extend the error-code table in `README.md` and `docs/api-reference.md`.

## Change 5 — Collapse the two near-identical axiom loops in `ArgumentEngine`

### Problem

`applyAxiomaticForcedAssignments` and `getAxiomaticBoundVariableIds` each walk `this.variables.toArray()`, filter by `isClaimBound`, look up the claim in the claim library, and gate on `claim?.type === 'axiomatic'`. They are nearly identical and diverge only in what they produce. Two issues:

1. Drift risk — if the predicate changes (e.g., the axiom-forcing rule is later refined), one loop can be updated and the other missed.
2. Duplicate `claimLibrary.get` calls per variable on every `evaluate()` / `checkValidity()` call. Negligible cost today, but free to fix.

### Evidence

- `src/lib/core/argument-engine.ts:2299-2327` (`applyAxiomaticForcedAssignments`).
- `src/lib/core/argument-engine.ts:2334-2347` (`getAxiomaticBoundVariableIds`).

### Proposed change

Extract a single private helper:

```ts
private collectAxiomaticBoundVariables(): TClaimBoundVariable[] {
    const out: TClaimBoundVariable[] = []
    for (const variable of this.variables.toArray()) {
        const v = variable as unknown as TCorePropositionalVariable
        if (!isClaimBound(v)) continue
        const claimBound = v as unknown as TClaimBoundVariable
        const claim = this.claimLibrary.get(
            claimBound.claimId,
            claimBound.claimVersion
        )
        if (claim?.type === "axiomatic") out.push(claimBound)
    }
    return out
}
```

`applyAxiomaticForcedAssignments` reduces to a loop over the helper's result (now incorporating the `Object.hasOwn` fix from Change 2). `getAxiomaticBoundVariableIds` becomes `.map(v => v.id)` over the same.

Bundle with Change 2 since both touch the same code region.

### Test plan

No new tests — the existing axiom evaluation and `checkValidity` carve-out tests cover both call sites. Refactor must leave the test suite green.

## Out of scope (recorded for transparency, not pursued)

- **`detectAllCycles` O(N²) path allocation** in `ClaimCitationLibrary`. Real, but only matters on pathologically deep citation graphs which are not a realistic shape for this library. Not landing without a benchmark motivating it.
- **`CoreClaimCitationSchema` / `CoreClaimAxiomSchema` structural duplication.** They diverge in description only today, but the design intent is that each can later add specialization (e.g., branded types, `additionalProperties` restrictions). Collapsing them now would lock in the wrong abstraction.
- **`PropositCore.forkArgument` claim destructure via `as Record<string, unknown>`.** Works for the v0.12 schema. Migrating to an explicit clone helper is a refactor with no behavioral change; leave for when the claim schema next changes.
- **Pre-existing `citations.json` shape validation in the migration.** Defensive; the actual code path only triggers when the v0.10 migration left a stale empty file, which is benign (gets re-checksummed in place). Not worth the schema-dependency at this site.
- **CLI `--axiom-id` ↔ `supportingClaimId` mapping in README.** Documentation-only, can be folded into the next docs sweep rather than a code-change request.
