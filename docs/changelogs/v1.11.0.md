# v1.11.0

Commit range: `v1.10.0..v1.11.0`.

## Added

- `executeStage(pipeline, stageId, upstream, input, deps)` — runs one stage of a pipeline against a caller-supplied map of upstream `{ outcome, output? }` records, reproducing the monolithic run's `ctx.get` / `ctx.stageStatus` semantics without re-running the DAG. Parses `input` via `Value.Parse(pipeline.inputSchema, input)` and seeds the parsed value into `ctx.input` (parity with `executePipeline`). Emits the per-stage events only (no `pipeline:*` bookends). Throws `PipelineConfigurationError` (`UNKNOWN_STAGE`) for an unknown stage id and throws a `GET_OUTSIDE_DEPS` / `STATUS_OUTSIDE_DEPS` config error out directly. Normalizes away `output` for non-`completed` upstream records and accepts a superset of records (uses the stage's own `dependsOn`).
- `executeFinalize(pipeline, upstream, input, deps)` — symmetric entry point for the multi-parent finalize step. Applies the same `finalizeRequiredOk()` gate and `FINALIZE_UNCAUGHT_ERROR` capture as `executePipeline`'s finalize; emits no events; `async` only for signature symmetry (`TPipelineFinalize.run` stays synchronous).
- New public types `TStageOutcomeRecord`, `TExecuteStageDeps`, `TExecuteStageResult`, `TExecuteFinalizeResult`, exported from `src/lib/pipelines/` and the package root.
- `UNKNOWN_STAGE` added as a member of the `PipelineConfigurationError.code` union (additive).
- `launchStage(pipeline, stageId, upstream, input, deps, attempt?)` — the launch half of the launch/complete split for an LLM-background stage: rehydrates `ctx`, builds the request via the shared seam, submits via `deps.submitBackgroundResponse`, and returns `{ responseId, status }` (`TLaunchStageResult`) WITHOUT awaiting. Emits `stage:start` / `stage:llm-request` / `stage:llm-response-created` (no `stage:end`). Throws if the submit dep is absent or `stageId` is not an LLM stage.
- `completeStage(pipeline, stageId, retrieved, deps, attempt?)` — the complete half: parses the RAW `retrieved.output` text against the stage schema, classifies a non-`completed` status per the launch/complete table (mirroring the OpenAI provider; `failed` → fail-fast, `content_filter` → fail-fast, `cancelled` → `skipped`, `max_output_tokens` → transient), and returns a `TExecuteStageResult` with `retryReason` (a reason code) on a retryable failure + `retrieved.tokenUsage` attached directly. Emits `stage:llm-call` / `stage:end` (no `stage:start`).
- `retryReason?: TRetryReason` added to `TExecuteStageResult` (set only by `completeStage`); `submitBackgroundResponse?` typed dep added to `TExecuteStageDeps` (function-type only — `src/lib/` takes no OpenAI import); `TLaunchStageResult` added. Framework-side `TResponseStatus` / `TRetrievedResponse` types added in `src/lib/llm/types.ts` (structural mirrors of the OpenAI extension's, so `src/lib/` references a retrieved-response status by type without importing the extension).
- `submitBackgroundResponse(req, options)` — new OpenAI-extension function: submits a background response (`{ background: true, store: true }`) and returns `{ responseId, status }` at submit WITHOUT polling/streaming to completion (the submit-only half of `runBackground`, including the terminal-on-submit fast-path + the no-tools guard). Exported from the openai extension barrel.
- Additive `incompleteReason?` / `errorMessage?` fields on `TRetrievedResponse` (the openai extension type), surfaced by `retrieveResponse` from `envelope.incomplete_details.reason` / `envelope.error.message`.

## Changed

- Refactored `executePipeline` to call extracted, module-level `runOneStage(stage, ctx, state)`, `runFinalize(pipeline, ctx, state)`, and `makeStageContext(state, allowedDeps, label)` with an explicit `TStageRunState` threaded through (`{ records, failures, signal, emit, generateId, llm, input, setConfigError }`) rather than closure-captured locals. `executeStage` / `executeFinalize` reuse the same bodies — one source of truth for stage and finalize execution semantics, no behavior change (the existing `executePipeline` suite stays green). The config-error disposition differs only via the `setConfigError` seam: the whole-DAG scheduler captures + re-throws after its bookends; the single-stage path throws immediately.
- Carved a **package-internal** seam out of `llmStage`'s body: `buildLlmRequest(cfg, ctx, userMessage?)` (prompt-build + `TLlmRequest` assembly), `validateLlmOutcome(cfg, rawText, status, incompleteReason)` (parse → `Value.Check` → outcome/retry classification), the shared `applyRetrySuffix` helper, and a `checkLlmOutput` core. The in-process `llmStage.run` retry loop now drives these same functions; `launchStage` / `completeStage` call them too — one implementation for prompt assembly + output validation. **`llmStage`'s public return type stays `TStage<TOutput>` (NOT widened);** the resolved config rides a non-enumerable, internal-symbol-keyed carrier recovered by the package-internal `readLlmStageConfig`. The seam fns + carrier/accessor are NOT exported. Behavior-preserving — the existing `llmStage` / `executePipeline` / ingestion suites stay green.
