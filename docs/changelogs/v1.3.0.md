# v1.3.0 changelog

Commit range: `1bb068d..v1.3.0` (post v1.2.0).

## Added

### v2-multi-stage ingestion pipeline (`src/extensions/argument-ingestion/v2-multi-stage.ts`)

- `createIngestionV2Pipeline(extension): TPipeline<TIngestionInput, TParsedArgumentResponse>`
  wires the 12-stage DAG defined in the ingestion-pipeline overview spec §7.2.
  4 deterministic stages + 8 LLM stages; finalize declares
  `claim-canonicalization` + `variable-assignment` + `formula-compilation`
  as required deps and `claim-type-classification`, `relation-extraction`,
  `conclusion-selection`, `formula-validation`, `claim-reference-validation`
  as optional deps.

### 12 stage modules under `src/extensions/argument-ingestion/stages/`

- **`segmentation`** (`segmentation.ts`) — `gpt-5.4-mini` LLM stage; splits raw input into sentence-or-thereabouts segments.
- **`claim-mention-extraction`** (`claim-mention-extraction.ts`) — `gpt-5.4` LLM stage; extracts un-deduplicated claim mentions per segment.
- **`citation-source-detection`** (`citation-source-detection.ts`) — `gpt-5.4-mini` LLM stage; detects Markdown links + "according to" patterns + bracketed citations.
- **`axiom-indicator-detection`** (`axiom-indicator-detection.ts`) — `gpt-5.4-mini` LLM stage; detects "by definition" / "necessarily true" / etc.
- **`claim-canonicalization`** (`claim-canonicalization.ts`) — `gpt-5.5` (reasoning_effort=medium) LLM stage; factory parameterized on `extension.claimSchema` so the per-claim output carries the extension's discriminated-union shape. Drafts the `suggestedSymbol` for each claim.
- **`claim-type-classification`** (`claim-type-classification.ts`) — `gpt-5.4` LLM stage; refines the canonicalizer's per-claim type with the citation + axiom evidence.
- **`claim-reference-validation`** (`claim-reference-validation.ts`) — deterministic stage; audits miniId collisions, dangling mappings, empty mention ids / lists.
- **`variable-assignment`** (`variable-assignment.ts`) — deterministic stage; symbol-validation regex `/^[a-zA-Z_][a-zA-Z0-9_]{0,31}$/` with `p<n>` fallback that skips integers already used by valid suggested symbols.
- **`relation-extraction`** (`relation-extraction.ts`) — `gpt-5.5` (reasoning_effort=high) LLM stage; emits support / joint-support / derivation-support relations.
- **`conclusion-selection`** (`conclusion-selection.ts`) — `gpt-5.5` (reasoning_effort=medium) LLM stage; returns `conclusionMiniId: null` when ambiguous.
- **`formula-compilation`** (`formula-compilation.ts`) — deterministic stage; per-relation compilation rules from spec §7.3 + dedicated conclusion-premise minting.
- **`formula-validation`** (`formula-validation.ts`) — deterministic stage; re-parses each compiled formula via `parseFormula` and verifies every atom resolves to a known variable symbol.

### Shared schemas (`src/extensions/argument-ingestion/stages/schemas.ts`)

- Per-stage TypeBox `outputSchema` definitions matching the spec §7.2 output column.
- `STAGE_IDS` const map naming every stage id used across the v2 pipeline.
- `SpanSchema` (`{ start, end }` object) — segmentation / mention / citation / axiom spans use a named-key object rather than `Type.Tuple([Number, Number])`. The tuple shape is not in the OpenAI structured-output converter's supported subset; the named-key form is also more LLM-friendly. See "Bug fixes" below.

### Finalize (`src/extensions/argument-ingestion/shared/finalize-response-v2.ts`)

- `finalizeResponseV2({ ctx, extension })` assembles a `TParsedArgumentResponse`-shaped output from per-stage outputs accumulated by the executor.
- Failure paths from spec §7.5: `{ argument: null, failureText: "No claims could be extracted from the input." }` when canonicalization is empty; `{ argument: null, failureText: "No single conclusion could be selected." }` when `formula-compilation.conclusionPremiseMiniId` is null.
- Role derivation per spec §7.4: `conclusion` / `premise` / `intermediate` derived from the relation graph + selected conclusion.

### Recording-provider v2 support

- `createRecordingLlmProvider(...)` accepts a new `fileName` option so v1 and v2 recordings live side-by-side in each fixture directory (`recorded-llm.json` vs `v2-recorded-llm.json`).

## Bug fixes

- **Recording-mode pipeline-null on every fixture (lambda-fold 1).** The OpenAI structured-output converter (`typeboxToOpenAiSchema`) does not support `Type.Tuple`; the initial v2 stage schemas used `Type.Tuple([Type.Number(), Type.Number()])` for `span` and `spans` fields. The throw from the converter ran synchronously at the top of the OpenAI provider's `respond` call, was classified as `LLM_NON_RETRYABLE_ERROR` by `llmStage` (no `retryReason` tag), and surfaced as a stage failure on `segmentation` after retry exhaustion. Every downstream stage with a required dep on `segmentation` cascade-skipped, the executor's `finalizeRequiredOk()` returned false on `claim-canonicalization` being `skipped`, and `output: null` came back in roughly 9 ms total per fixture with zero successful LLM calls. Fix: v2 stage schemas now use a named-key `SpanSchema` (`{ start, end }`) that the converter accepts; regression coverage in `test/extensions/argument-ingestion/stages/schema-converter-regression.test.ts` pins every v2 LLM stage's `outputSchema` through `typeboxToOpenAiSchema` so the same class of bug fails at unit-test time.

- **Array-rooted strict-mode schemas rejected by OpenAI (lambda-fold 3).** With the lambda-fold 1 converter throw gone, fixture recording reached the real OpenAI Responses API — which then returned 400 `invalid_json_schema`: "schema must be a JSON Schema of 'type: object', got 'type: array'". The OpenAI Responses-API strict-mode `text.format.schema` field requires the root to be `{ "type": "object" }`. 5 of the 8 v2 LLM stage outputSchemas (`segmentation`, `claim-mention-extraction`, `citation-source-detection`, `axiom-indicator-detection`, `relation-extraction`) were `Type.Array(...)` at the root. `classifyHttpError(400)` returns `NonRetryableLlmError` (no `retryReason`), so the same `segmentation` → cascade-skip → `output: null` chain repeated, only slower (84-926 ms per fixture because real HTTP roundtrips were involved). Fix: wrap each of the 5 stages' `outputSchema` in a single-key object envelope (`{ segments: [...] }`, `{ mentions: [...] }`, `{ sources: [...] }`, `{ axioms: [...] }`, `{ relations: [...] }`). Per-stage `buildPrompt(ctx)` consumers, the prompt instructions to the LLM, `finalize-response-v2`, and every test fixture were updated to read the envelope. The regression test now also asserts every LLM stage's converted-schema root is `{ "type": "object" }` so the same class of bug fails at unit-test time. Static type names (`TSegment`, `TClaimMention`, etc.) remain pointing at the per-item shape via `TXOutput["envelopeKey"][number]`, so consumer code that destructured items by name is unaffected.

- **Diagnostic dump on v2-e2e null output (lambda-fold 2).** The v2-e2e test now logs the executor's `stageOutcomes`, `failures`, and `tokenUsage` to stderr whenever `result.output === null`, in both record and replay modes. The bare `expect(result.output).not.toBeNull()` assertion previously told us _whether_ the pipeline succeeded but not _which stage_ failed; the dump surfaces the exact stage + failure code + message for diagnosis. Diagnostic-only — no behavior change on the happy path.

- **`Type.Record` outputs rejected by OpenAI strict mode (lambda-fold 4).** Recording attempt #3 made it past segmentation (4 stages completed in ~18 s of real HTTP traffic) but `claim-canonicalization` then hit a different strict-mode 400: "'required' is required to be supplied and to be an array including every key in properties. Extra required key 'mentionToClaim' supplied." OpenAI strict-mode JSON Schema doesn't support `additionalProperties` / `patternProperties` / arbitrary-key `Record`-style objects. The converter's `convertRecord` produces `{ type: "object", additionalProperties: <V> }`; even though our `properties` and `required` lists agree on the key, the API treats the inner schema as having no fixed properties and reports `required` as having "extra" keys. Fix: replace every `Type.Record(...)` in v2 LLM stage outputSchemas with explicit list shapes. `ClaimCanonicalizationOutputSchema.mentionToClaim` is now `Type.Array(Type.Object({ mentionId, claimMiniId }))`; `ClaimTypeClassificationOutputSchema` becomes `Type.Object({ classifications: Type.Array(Type.Object({ miniId, type, sourceString })) })` (also picking up the lambda-fold 3 object-envelope to satisfy the root-object constraint). Downstream readers (`claim-reference-validation`, `relation-extraction`, `conclusion-selection`, `finalize-response-v2`) iterate the lists; the ones that previously did keyed lookups build a `Map<string, ...>` on receipt. Test fixtures and the `v2-multi-stage` mock chain updated.

    The regression test (`schema-converter-regression.test.ts`) now also walks every LLM-stage's converted schema recursively and asserts three strict-mode invariants at every depth: no `additionalProperties` other than literal `false`; no `patternProperties` anywhere; every key in each `properties` map is also in `required` (and vice versa). 8 stages × 3 invariants = 24 assertions pinned. Future `Type.Record` regressions will fail at unit-test time, not at fixture recording.

- **v2-e2e replay-skip refinement.** The harness now requires both `v2-recorded-llm.json` AND `v2-expected.json` to be present for a fixture to run in replay mode; a `v2-recorded-llm.json` alone (indicating a partial recording from a crashed attempt) triggers a skip rather than a "no v2-expected.json" failure. The change lets the user iterate on recordings without false-positive CI failures.

## Changed

- **`conclusionSelectionStage` now emits `NO_SINGLE_CONCLUSION` via `ctx.addFailure`** (spec §7.2 row 10, lambda-fold 1). The stage was already exporting the `CONCLUSION_SELECTION_NO_CONCLUSION_FAILURE_CODE` constant but never calling `addFailure`. The stage now wraps the inner `llmStage`'s `run` and emits a `warning`-severity `ProcessingFailure` whenever the LLM returns `{ conclusionMiniId: null }`. The failure message defaults to the LLM's `rationale`; if rationale is empty, falls back to the canonical `"No single conclusion could be selected."`. The stage itself still completes successfully — the failure is an informational side-channel; the `argument: null` outcome is still driven by `formula-compilation.conclusionPremiseMiniId === null` flowing into `finalize-response-v2`.
