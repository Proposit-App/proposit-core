# v1.2.0 changelog

Commit range: `36be21a..v1.2.0` (post v1.1.1).

## Added

- New `stage:llm-call` variant on `TPipelineEvent` (`src/lib/pipelines/types.ts`).
  Fields: `kind`, `stageId`, `attempt` (1-indexed), `prompts: { system,
user }`, `output: unknown`, `tokenUsage: TLlmTokenUsage`,
  `validationError?: string`, `at: number`. Additive; no breaking change
  to the union — exhaustive `event.kind` switches in consumer code will
  need to add a branch.

## Changed

- `llmStage` (`src/lib/pipelines/stage-helpers.ts`) emits the new
  `stage:llm-call` event after every successful provider call, before
  the schema-validation retry/return branching. The event fires for
  schema-passing and schema-failing attempts; on failure the event
  carries the formatted TypeBox error string in `validationError` and
  the raw output is preserved in `output`. The retry loop's schema-
  validation branch was lightly refactored so `Value.Check` runs once
  and its outcome drives both the event payload and the retry decision
  (the prior shape computed `validationMessage` only in the failure
  branch, which would have required duplicating the error-string
  formatting at the emit site).
- `prefixSubPipelineEvent` in the same file extended to cover the new
  variant for exhaustiveness — same `stageId` prefixing as the other
  stage-keyed events.

## Tests

- `test/pipelines.test.ts`: four new tests under the
  `llmStage — stage:llm-call event` describe block — successful attempt,
  retry-then-succeed (two events, second carrying the retry-suffix in
  `prompts.user`), retry-exhausted (both events carry `validationError`,
  `stage:end` is `failed`), and the zero-event invariant on a
  `deterministicStage` run.
